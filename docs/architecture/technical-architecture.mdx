## Overview

Aegify is an evidence pipeline with a scanner CLI, normalized graph and evidence
models, isolated verification runners, and a Next.js dashboard.

```text
Workspace inputs
  repositories + manifests + SCIP + classpath + external results + runtime evidence
        |
        v
Identity and indexing
  repo/module/file/symbol IDs + content-addressed snapshots
        |
        v
Static and semantic analysis
  AST -> call graph -> CFG/ICFG -> SSA/DFG -> points-to/taint
        |                         |
        |                         +-> JVM/Spring/SCIP/bytecode overlays
        v
Attack-surface graph
  frontend -> Gateway -> endpoint -> finding -> runtime observation
        |
        +-> SARIF / JSON / dashboard
        +-> approved verification plan -> isolated runner -> normalized evidence
```

## Workspace layer

The workspace loader accepts one or more repositories and maps files to Maven or
Gradle modules. Repository IDs are explicit and stable. A deterministic snapshot
covers configuration, repository revisions, module relations, indexes, and
evidence artifacts.

File access is bounded to declared roots. Path normalization rejects absolute,
parent-traversal, symlink escape, and unsafe archive entries.

## Parsing and identity

Tree-sitter parsers produce normalized functions, calls, assignments, classes,
imports, annotations, literals, endpoints, and source ranges. IDs include
repository, module, file, owner, descriptor, and call site where applicable.

Parsing is file-parallel and deterministic. Unsupported syntax is counted and
retained as incomplete evidence rather than silently ignored.

## Graph layers

### Call graph

The call graph is a multigraph: repeated calls from the same caller to the same
callee retain different source call sites. Local resolution, import evidence,
SCIP, artifact providers, classpath methods, hierarchy dispatch, and framework
models contribute typed edges with fidelity and provenance.

### Program Graph

The Program Graph combines CFG, source-bounded ICFG, reaching definitions, SSA,
def-use, data-state transformations, and typed overlays. Query code selects edge
families explicitly. Context-balanced queries validate matching call and return
sites and enforce bounded state.

### Attack-surface graph

Attack-surface nodes represent frontend calls, Gateway routes, backend endpoints,
findings, and runtime observations. Edges retain public and transformed paths,
HTTP method, file/line, confidence, match kind, and evidence ID.

The dashboard can answer:

- Which public routes reach this endpoint?
- Is the endpoint called by known frontend code?
- Which findings lie on reachable code paths?
- Which paths have approved runtime observations?
- Which relations are compiler-exact versus fallback candidates?

## Semantic providers

### SCIP

SCIP supplies language-independent definition/reference and package information.
The importer implements exact symbol/package/version resolution and caches shards
by content hash. The generator planner isolates JVM build roots and pins the
indexer image.

### JVM and build systems

Maven property and dependency-management information and supported Gradle
literal/version-catalog/lockfile forms produce artifact coordinates. Unique
workspace providers can create cross-repository module edges. The classpath layer
adds SHA-bound JAR/class evidence, descriptors, dispatch candidates, allocation
evidence, selected bootstraps, and declared exceptions.

### Spring

The Spring provider resolves supported DI candidates and route behavior. It keeps
qualifier, primary, name, condition, module, and artifact evidence. Ambiguous
providers produce candidate sets and counters, never a fabricated exact edge.

## Rules

YAML rules normalize into `PatternSpec` and optional taint specifications. Strict
audit and runtime use the same normalization logic. CI requires every enabled
rule and every pattern to be executable. Versioned library model packs use a
separate strict source/sink/propagator/sanitizer schema.

Rule output becomes a finding only after location, repository/module, rule,
severity, message, and evidence provenance are available. Pattern and imported
fallback results default to `candidate/advisory`. Taint paths and supported
structured semantic detectors can emit `reachable/blocking` results. CI exits
non-zero only for blocking high or critical findings; severity alone never
promotes a candidate. Broad candidates remain queryable in SARIF, GitHub review,
and the dashboard.

## External evidence

SARIF, Semgrep, Joern, SCIP, HTTP, browser, proxy, HAR, and OTel adapters normalize
into bounded records. Artifact hashes and workspace snapshots prevent accidental
cross-version attachment. Imported paths and graph sizes are validated before
storage.

## Verification architecture

Verification has three layers:

1. a declarative plan describing runner, target, actions, bounds, and evidence;
2. a policy evaluator that requires approval and rejects unsafe targets/actions;
3. a runner that executes in Docker or a loopback-only subprocess and emits a
   hashed, redacted evidence artifact.

Docker plans pin image digests, disable network by default, drop capabilities,
set `no-new-privileges`, use a read-only root where possible, and enforce CPU,
memory, process, timeout, output, and artifact limits. Browser plans permit only
bounded navigation, click, and wait actions. Arbitrary JavaScript and form filling
are not accepted in the alpha contract.

## Dashboard

The dashboard is a Next.js application with Prisma and libSQL/SQLite for the
default self-hosted profile. Production startup requires independent auth and
encryption secrets, a valid HTTP(S) `AUTH_URL` origin, and a complete GitHub or
GitLab OAuth provider. CI upload uses a separate bearer token.

SARIF ingestion preserves Aegify provenance, workspace snapshots, evidence state,
and gate disposition. The data model stores projects, scans, findings, endpoints,
graph data, rules, and LLM jobs. Findings can be filtered as blocking or advisory.
The production image runs as uid 1001/gid 1001 and contains no build-only secret.

## Storage

The scanner exposes backend interfaces for SQLite, PostgreSQL, and object storage
where configured. Content hashes deduplicate artifacts and support evidence
integrity. Storage paths and bucket keys are derived from validated identifiers.

The alpha does not claim hostile multi-tenant isolation. Separate instances or
strong infrastructure boundaries are recommended for unrelated organizations.

## CI and release architecture

- Scanner: locked uv install, formatting, lint, strict typing, strict rule audit,
  tests with coverage, and wheel build.
- Dashboard: script-free npm install, advisory audit, Prisma generation and fresh
  migration, tests, lint, and production build.
- Containers: digest-pinned base images and hardened scanner smoke.
- Security: CodeQL, dependency review, Gitleaks, Scorecard, and zizmor.
- Release: wheel, SBOM, checksums, and GitHub artifact attestations.

Third-party Actions are pinned to full commit SHAs. Workflows use least-privilege
permissions, hardened runners, bounded timeouts, and non-persistent checkout
credentials.

## Scaling model

- Parse files independently and cache by content hash.
- Shard SCIP indexes and analysis by repository/module.
- Reuse manifest, classpath, and artifact-provider snapshots.
- Bound graph queries and importer sizes.
- Preserve unresolved counters to detect fidelity loss at scale.

A distributed graph store is not required for alpha. The normalized IDs and
contracts allow future storage backends without changing evidence semantics.

## Accuracy and maturity boundary

Aegify alpha provides executable semantic evidence and bounded verification. It
does not claim exhaustive language semantics, full CPG equivalence, IFDS/IDE,
unified source/bytecode heap propagation, or autonomous exploit proof. Those
capabilities are explicit post-alpha precision milestones.
