## Scope

This threat model covers the scanner, dashboard, CI/release pipeline, imported
evidence, and verification runners in the self-hosted open-source alpha.

## Assets

- Private source code and dependency metadata.
- Findings, attack-surface graphs, runtime evidence, and reports.
- Dashboard user, project, and scan data.
- OAuth, upload, LLM, DefectDojo, Vault, database, and storage credentials.
- CI tokens, release artifacts, SBOMs, and attestations.
- Integrity of rule packs, indexes, classpath artifacts, and workspace snapshots.

## Trust boundaries

1. Repository content entering the scanner.
2. External SARIF/JSON/SCIP/archive artifacts entering adapters.
3. Scanner output entering the dashboard or third-party integrations.
4. Browser, HTTP, proxy, build, and Docker verification execution.
5. Dashboard clients and authenticated APIs.
6. CI runners, Actions, registries, and release publication.
7. Optional LLM and external reporting providers.

## Threats and controls

| Threat | Primary controls | Residual risk |
|---|---|---|
| Malicious source exploits a parser | Non-executing parsers, bounded input, updated dependencies, isolated CI | Native parser/library vulnerabilities remain possible |
| Path traversal or archive escape | Repository-relative normalization, traversal/symlink/duplicate/compression bounds | New formats require equivalent validation |
| Graph or evidence denial of service | File/result/node/edge/size/time/state limits | Large legitimate workspaces may require tuning |
| Ambiguous edge creates false reachability | Fidelity labels, exact resolution preference, unresolved/ambiguous counters | Conservative candidate paths can still increase triage load |
| Rule field is accepted but not executed | Shared normalization, strict schema, per-pattern executable audit | New DSL features need tests in audit and evaluator |
| Runtime verifier reaches an unintended target | Explicit approval, loopback default, destination/action allowlists, no-network containers | Expanded future policies require additional review |
| Verification escapes container | Digest pinning, non-root, cap-drop, no-new-privileges, read-only root, resource limits | Container runtime/kernel risk remains |
| Credentials leak into evidence or logs | Dedicated secrets, redaction, value hashing, ignored local files, Gitleaks | Application-specific sensitive fields need configuration |
| Unauthenticated dashboard access | Production fail-closed auth, OAuth, valid `AUTH_URL`, protected routes | Auth.js beta dependency requires ongoing review |
| CI pull request steals token | Read-only defaults, non-persistent credentials, SHA-pinned Actions, restricted approval permissions | Platform or pinned Action compromise remains possible |
| Dependency or image substitution | Lockfiles, digest-pinned bases, Dependabot, dependency review, SBOM/attestation | Package registries and transitive build dependencies remain trusted |
| Malicious imported result forges provenance | Artifact hash and workspace snapshot, producer/fidelity fields | A trusted producer can still emit incorrect analysis |
| LLM exfiltrates source or hallucinates proof | Optional/off by default, bounded context, evidence-state separation | Configured provider receives selected context |

## Dashboard production controls

Production startup requires:

- `AUTH_SECRET`;
- `ENCRYPTION_SECRET`;
- valid origin-only `AUTH_URL` using HTTP or HTTPS;
- a complete GitHub or GitLab OAuth pair;
- dedicated `AEGIFY_UPLOAD_TOKEN` for CI upload.

Values must be independent. Vault Agent or another secret manager should inject
them at runtime. The final image must not contain build-only values.

## Verification authorization

Possession of a repository does not imply authorization to test deployed systems.
Verification plans must target owned fixtures or explicitly authorized systems.
The alpha policy is loopback-first and rejects broad external targets. Exploit
impact proof is a separate approval state from static analysis or observation.

## Assumptions

- The host, container runtime, CI platform, and configured identity provider are
  administered by trusted operators.
- Related repositories supplied to one workspace are authorized for joint analysis.
- Operators protect backups, database files, object storage, and Vault.
- Multi-tenant hostile isolation is provided by infrastructure, not by the alpha.

## Security reporting

Use GitHub private vulnerability reporting as described in
[security reporting policy](/security/reporting). Do not publish a zero-day, credential, private
source fragment, or sensitive runtime request in a public issue.
