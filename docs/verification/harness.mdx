Aegify verification converts an approved hypothesis into bounded runtime
evidence. It is not enabled implicitly by a static finding, and it does not grant
authorization to test a third-party system.

## Evidence states

- `candidate`: static or imported finding.
- `reachable`: bounded graph path.
- `observed`: approved runner exercised a request, route, or trace.
- `impact_proven`: separately authorized security impact demonstration.

Harness execution normally produces `observed` evidence. Promotion to
`impact_proven` requires an explicit policy and reviewer decision.

## Plan contract

A plan declares:

- runner type and immutable runtime image where applicable;
- target service or loopback origin;
- allowed commands, requests, browser actions, or proxy mutations;
- network, filesystem, capability, and process policy;
- CPU, memory, timeout, output, response, redirect, and artifact limits;
- redaction and evidence destination;
- approval identity and scope.

Examples are available in `examples/verification-*.yml`.

## Docker runner

The Docker runner requires an image digest and rejects mutable-only image names.
The default policy uses:

- network disabled;
- read-only root filesystem;
- non-root user;
- all capabilities dropped;
- `no-new-privileges`;
- bounded CPU, memory, pids, timeout, stdout/stderr, and artifacts;
- allowlisted executable and arguments;
- an ephemeral copy of approved input.

Artifacts are path-checked, size-bounded, hashed, and copied out before the
container is removed. The planner and executor record the exact digest and argv.

## JVM build and index runners

Maven/Gradle classpath export and `scip-java` indexing operate per independent
build root. Build commands require approval and use supported offline arguments
where possible. Output archives and indexes are treated as untrusted imports:
path traversal, duplicate names, unexpected repositories, hash mismatch,
compression bombs, and oversized artifacts are rejected.

## HTTP runner

The active HTTP runner is loopback-only by default. It supports a bounded method,
path, headers, and body contract. Redirects are disabled or constrained, response
size is capped, and cookies/authorization are not persisted. Evidence stores
status, selected headers, duration, and response digest.

## Browser runner

The Playwright runner permits a small action set:

- navigate to an allowed loopback origin;
- click an approved selector;
- wait for an approved selector or bounded duration.

Arbitrary JavaScript execution and unrestricted form filling are rejected. Any
request to an unapproved origin aborts the run. Browser network evidence is
redacted and normalized before import.

## Proxy runner

The loopback proxy can mutate approved method, path, query, header, raw body, or
JSON fields. It rejects external targets and sensitive headers. Query/body values
are represented by hashes when the value is unnecessary for correlation.

Proxy evidence records the mutation type, redacted target, response status,
content digest, and linked endpoint. A mutation response is an observation, not
automatic proof of a vulnerability.

## Example policy

```yaml
version: 1
runner: http
approval:
  required: true
target:
  origin: http://127.0.0.1:8080
request:
  method: GET
  path: /health
limits:
  timeout_seconds: 10
  response_bytes: 1048576
evidence:
  redact_headers: [authorization, cookie, set-cookie]
```

The exact schema and supported commands are versioned with the scanner. Validate
plans with the current CLI before committing them.

## Operational checklist

1. Confirm target ownership and authorization.
2. Pin repository snapshot, image digest, tool version, and plan hash.
3. Review destinations, actions, mutations, resources, and redaction.
4. Record explicit approval.
5. Execute in an isolated runner.
6. Validate output bounds and artifact hashes.
7. Import evidence with repository/module/workspace provenance.
8. Remove temporary containers, volumes, copies, and credentials.
9. Report the resulting evidence state without overstating impact.

## Current alpha boundary

The implemented browser, HTTP, and proxy flows focus on loopback and owned
fixtures. Authenticated sessions, TLS interception, arbitrary multi-origin flows,
and automated exploit impact proof are post-alpha capabilities and will require a
stronger policy and secret-handling model.
