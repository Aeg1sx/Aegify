This document describes the executable semantic layers in the Aegify alpha and
the boundary between exact evidence, conservative modeling, and fallback edges.

## Repository and module identity

Every file, symbol, endpoint, call site, graph node, and finding is qualified by
repository and module. Same-named packages or classes in different repositories
remain distinct. A workspace snapshot hashes repository identities, revisions,
manifests, indexes, and configured evidence.

For monorepos, Maven and Gradle build roots produce module membership and module
dependency relations. Same-repository membership alone does not authorize a
cross-module call edge.

## Cross-repository resolution ladder

Aegify resolves a reference using the best available evidence:

1. **SCIP exact symbol**: scheme, package manager, package name, package version,
   descriptor, definition, and occurrence identify a target.
2. **Artifact provider**: an exact Maven/Gradle coordinate maps to one workspace
   module at a compatible version.
3. **Compiler classpath**: a SHA-bound classpath snapshot maps a source owner and
   descriptor to a unique class or method.
4. **Declared dependency fallback**: an explicit repository relation allows a
   lower-fidelity candidate link.

Version conflicts, multiple providers, unresolved descriptors, and truncated
indexes are recorded in SARIF and workspace statistics. Aegify does not choose a
random provider to make a path complete.

## SCIP

The importer supports official SCIP symbol structure and external symbols. Index
shards are cached by content hash and invalidated when inputs change. Multiple
indexes can coexist for different modules and repositories.

The JVM index planner discovers independent build roots and creates digest-pinned
`scip-java index` plans. Generated indexes are artifacts with retained hashes;
planning never implies the command was run.

## JVM source semantics

### Callable identity and overloads

Java and Kotlin functions receive descriptor-aware identities. Resolution uses
owner, method name, arity, literal/local type hints, imports, inheritance, Kotlin
default arguments, and varargs. Exact matches are preferred; ambiguity remains
explicit.

### Hierarchy and dispatch

- Direct/static calls use exact owner and descriptor evidence when available.
- Class Hierarchy Analysis conservatively preserves possible virtual/interface
  implementations.
- Rapid Type Analysis narrows targets using observed allocation sites while CHA
  remains available as coverage evidence.
- Inherited methods and default implementations are deduplicated.
- Supported `LambdaMetafactory` and `altMetafactory` records resolve lambda and
  method-reference targets.
- Unknown bootstrap methods stay unresolved.

### Bytecode import

Classpath snapshots are strict JSON documents bound to SHA-256. Archives and
class files are module-scoped and bounded by file count, method count, byte size,
path safety, compression ratio, and duplicate detection. The parser imports
methods, descriptors, selected invoke opcodes, `NEW`, bootstrap metadata, and
declared exceptions.

The host-side materializer validates every artifact before exposing it to the
workspace. Maven/Gradle exporters run only from approved build roots with
allowlisted arguments and pinned images.

## Spring model

Aegify models:

- `@Component`, `@Service`, `@Repository`, `@Controller`, and related stereotypes;
- Java and Kotlin constructor and field injection;
- `@Bean` factory providers;
- `@Qualifier`, `@Primary`, injection-name preference, and ambiguous candidates;
- module/artifact provider scope and cross-repository auto-configuration;
- `@Profile`, `@ConditionalOn*`, and related condition evidence;
- selected Spring Security guards and transaction proxies;
- suspend handlers and selected Reactor propagation.

Conditional providers remain conditional unless the workspace supplies exact
activation evidence. Custom condition code is not executed.

## Spring routes and Gateway

Spring MVC/WebFlux detection combines class and method mappings, supports named
`path`/`value` attributes, HTTP methods, and Kotlin suspend handlers.

Gateway modeling reads supported YAML and Java/Kotlin DSL routes. It records host,
path, and method predicates plus transformations such as `RewritePath` and
`StripPrefix`. The public path and transformed backend path remain separate graph
objects with source provenance.

## Program Graph

The Program Graph is a typed multigraph rather than a claim of full CPG parity.
It includes:

- AST-derived symbols and structural relations;
- call graph edges with call-site identity;
- CFG edges for branches, loops, switch/when, break/continue, and conservative
  exception constructs;
- ICFG call, normal return, and selected declared-exception return edges;
- reaching definitions, SSA phi, def-use, and data-state transformation edges;
- endpoint, route, frontend, runtime, and semantic overlays.

Context-balanced queries push a call-site token on call edges and require the
same token on return edges. Maximum call depth, state count, and path length are
bounded. Exhaustion raises an explicit result instead of returning false.

## Points-to and taint

The JVM source points-to analysis uses allocation-site identity and a k=2 call
string. It propagates parameters, receivers, scalar returns, selected object
returns, fields, and library summaries. Singleton allocation fields support
strong update; ambiguous sets remain weak updates.

Global taint v2 is flow-sensitive for supported local and field operations and
uses points-to identity to avoid obvious cross-object contamination. Sources,
sinks, propagators, and sanitizers come from strict, versioned model packs. Taint
evidence records call context and the source-to-sink path.
Sink models can select either a specific argument or the call receiver. This
distinguishes an untrusted format program in `template.format(value)` from safe
substitution data in `'value={}'.format(untrustedValue)`.

Regression tests cover caller isolation, factory-return receivers, field stores
and loads, exact imported targets, safe overwrite, sanitizer categories, and
nearby decoys.

## Heuristic call graph language contract

All parser-supported languages—Python, JavaScript, TypeScript, Java, Go, Rust,
Swift, and Kotlin—produce call-graph nodes and resolved intra-file edges. Import
resolution is repository-scoped and recognizes language-native dotted, slash,
and `::` module forms, JS/TS extensionless relative imports, directory index
modules, Go package directories, Rust `crate` paths, and aliased Python/JS/TS
imports. Ambiguous same-name targets remain unresolved instead of being guessed.

This is a source-level heuristic graph. `Yes` in the support matrix means the
parser-backed contract test succeeds for that language; it does not mean
compiler-accurate virtual dispatch, reflection, generated-code, or runtime
framework completeness.

## Frontend and runtime correlation

Static frontend extraction recognizes supported `fetch` and axios-style calls,
including bounded string/template construction. Calls are linked to direct
backend routes or to public Gateway routes followed by a transformation edge.

Runtime HTTP/browser/proxy/HAR/OTel observations attach to endpoints using exact
or normalized route evidence. They do not change a static finding into exploit
proof. The evidence state is preserved as candidate, reachable, observed, or
impact-proven.

## Current limits

- No exhaustive unified source-and-bytecode heap domain.
- No general IFDS/IDE tabulation.
- Runtime and implicit exception behavior is not exception-complete.
- Generic substitution, Kotlin extensions, reflection, dynamic proxies, and
  arbitrary invokedynamic bootstraps are conservative.
- Dynamic Gateway and frontend URL construction can remain unresolved.
- Framework model coverage is intentionally versioned and incomplete.
