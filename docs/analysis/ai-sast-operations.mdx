AI review in Aegify is an enrichment layer. It cannot close, confirm, suppress,
or raise the evidence state of a finding. A deterministic scanner result and a
human triage decision remain authoritative.

## Structured review contract

Every AI review records one of `likely_true_positive`,
`likely_false_positive`, or `needs_review`, plus:

- supplied evidence for and against the conclusion;
- explicit evidence gaps;
- a bounded attack scenario that is not described as observed impact;
- concrete remediation, corrected code, and ordered fix steps;
- an owned-fixture-only proof plan with approval, preconditions, expected
  signal, and a negative control;
- model, prompt digest, and tool evidence when the scanner-side orchestrator is used.

The dashboard stores this as a suggestion. A user must separately accept or
reject the suggestion through the finding lifecycle.

Dashboard AI review runs as a separately tracked `LlmJob`; it never rewrites
the deterministic source scan status. Next.js tracks the post-response task,
provider requests have a bounded timeout, and abandoned jobs are failed after
the execution bound. A model must return one valid review per supplied finding.
Omitted or failed batches produce `partial` or `failed`, never a false
`completed` state. `needs_review` remains unresolved and is not counted as a
true positive. Provider responses and parsed review counts are size-bounded,
including for custom endpoints that ignore requested token limits.
Each persisted review names its producer, provider, model, and prompt digest.
Suggested remediation stays inside the AI review record and does not overwrite
the scanner-authored remediation field before human acceptance.
The database also holds a nullable unique lease for each active scan review, so
concurrent requests cannot create duplicate provider work or conflicting
updates.

## Repository source scan

The dashboard's **Start source scan** action now queues the deterministic Python
engine used by the CLI. A separate worker fetches and seals a source snapshot,
records progress and publishes results atomically. See
[worker operations](/operations/self-hosted-workers) for installation, recovery,
resource bounds and source retention. Source scanning does not require an AI key.

## Historical repository AI candidates

The earlier repository AI workflow resolved the selected GitHub or GitLab ref to
an immutable commit before reading its tree or files. Its model responses were not
stored merely because they were valid JSON: the rule ID, file path, approximate
line, and redacted code snippet must bind back to the exact fetched source
batch. Historical records remain available; new repository scans use the common
SAST engine. AI supplied-finding reviews remain separate from deterministic scans.

These records use `repo-ai-candidate`, `candidate`, and `advisory`. They do not
replace the deterministic scanner or establish reachability. Provider tree
truncation, file/byte bounds, model output bounds, or a failed batch make the
scan `partial` or `failed`. An incomplete or non-default-branch scan may add
observed candidates but cannot mark unseen older candidates absent; only an
exhaustive successful default-branch snapshot can reconcile project-level
absence and current-occurrence state.

## Allowlisted analysis tools

`aegify.llm.tools.ToolRegistry` accepts only explicitly registered, read-only
Python handlers. The built-in registry provides bounded finding context, call
paths, attack-surface evidence, multi-repository workspace summaries, source
navigation, and non-executing harness plans. Unknown tools, write-capable specifications,
oversized arguments, and oversized results are rejected. Common credential
shapes are redacted before model use and before generated output is persisted.
The call-path tool and agent trace share one structural completeness check:
the entry handler, repository and source range must match; every symbol and
directed link must be present; and the entire finding range must fit the sink.
Legacy or disconnected paths remain incomplete. Paths beyond 100 steps carry an
explicit truncation flag and evidence gap. This describes the supplied static
artifact; runtime observations and demonstrated impact have separate evidence states.
Direct provider credentials are never forwarded to custom gateway endpoints;
those endpoints receive only their explicitly configured headers. Destructive
proof templates are replaced with a blocked marker instead of being displayed
as runnable guidance.

Custom tools are application code, not model-generated shell commands:

```python
from aegify.llm.tools import ToolRegistry, ToolSpec

registry = ToolRegistry()
registry.register(
    ToolSpec(name="ownership_context", description="Return reviewed ownership metadata"),
    lambda arguments, context: {"team": "payments", "read_only": True},
)
```

Do not register filesystem writes, network mutation, shell execution, secret
retrieval, or deployment actions as AI review tools.

## Multi-repository AI scan

Use a versioned workspace manifest so repository identity and dependencies are
part of the evidence snapshot:

```bash
aegify scan-workspace aegify-workspace.yml \
  --ai-tools \
  --model claude-opus-5 \
  --max-ai-findings 50 \
  --output sarif \
  --output-file results.sarif
```

The reviewer can inspect each tool result and request further evidence before
returning its structured suggestion. The default permits eight tool calls over
four exploration rounds and at most one final review call. Repeated identical
requests reuse retained evidence and still consume the call budget. Exhausted
budgets, unavailable models and unsupported citations produce `needs_review`.
Token budget and finding count also bound work. Source and tool output are
treated as untrusted data, not prompt instructions.

### Source navigation and references

`scan-workspace --ai-tools` admits source already parsed by the scanner. Capture
checks each file against the parser's SHA-256 and retains a redacted, immutable
in-memory snapshot. Tools read only that snapshot. They cannot load arbitrary
paths, hidden files, unparsed files, filesystem links or special files. Capture
uses descriptor-relative opens on Linux and macOS; platforms without those
primitives report unavailable source. Changes before capture fail the digest
check; changes afterward do not alter the retained evidence.

| Tool | Purpose | Bound and continuation |
|---|---|---|
| `source_list_files` | Discover files by repository and path prefix | 25 files per page; `next_offset` |
| `source_read` | Read a precise source range | 200 lines and 16 KiB; truncation is explicit |
| `source_search` | Find literal, case-sensitive text in redacted source | 200 files, 4 MiB, 20 matches; `next_cursor` |
| `source_symbols` | Locate parsed function declarations | 10 declarations per page; `next_offset` |

Capture retains at most 2,000 files, 512 KiB per file and 32 MiB in total. Missing
or excluded material is reported in the source catalog, separately from SAST
coverage. A symbol lookup supplies declaration metadata; the reviewer must read
source before citing it. Search does not interpret regular expressions or execute
repository code. Known credential shapes are redacted before line selection;
line numbers remain tied to the original file. Redaction is not a general-purpose
data-loss-prevention guarantee: configure providers permitted to receive the
selected project source.

Source reads issue citation IDs bound to repository, relative path, original
source digest, line range and redacted excerpt digest. The model selects these
IDs; it cannot supply a new location. The executor checks them against retained
tool results and the snapshot. A non-abstaining review must include a reference
covering the supplied finding's repository and entire range. A valid reference
establishes which code was read; it does not establish that the model's reasoning
is correct or that runtime impact occurred.

### Review activity in the dashboard

SARIF uploads preserve source references and tool spans with the AI suggestion.
The finding page shows retained excerpts with line numbers, source and excerpt
hashes, model-call counts, rounds, tool success/failure, truncation, cache reuse
and elapsed tool time. Expand **Review provenance** for source-manifest and prompt
digests. Older reports without these fields remain readable. Imported references
are producer-supplied evidence, not a new independent verification by the dashboard.

Aggregate tool evidence is capped at 96 KiB, each prompt at 128 KiB and each
structured model response at 64 KiB. An oversized prompt is not partially sent.
Tool argument and result digests support comparison; raw provider credentials
are not part of the source snapshot. Scanner-authored remediation and workflow
state remain unchanged; proposed fixes stay inside the AI suggestion.

This source loop currently serves the scanner's workspace AI review. Dashboard
provider reviews and the six-role agent narratives have separate execution paths;
they do not yet inherit this source loop. Contract tests use scripted model
responses and owned source fixtures. Live-provider behavior, calibrated model
confidence and cross-model quality remain separate acceptance work.

## Finding lifecycle

Project-linked SARIF uploads preserve prior scans. A stable producer fingerprint
is preferred; Aegify derives a content-based fallback when the producer does not
provide one. The current occurrence is classified as `new`, `unchanged`,
`updated`, or `regressed`.

Only current occurrences appear in default project lists and statistics. The
history toggle exposes previous occurrences. False-positive and accepted-risk
decisions require a rationale, may have an expiry, and create an actor-stamped
audit event. A fixed or false-positive finding that reappears after absence is
reopened by the system and audited.

## Precision and recall gate

Use owned, versioned ground truth to measure scanner behavior instead of using
model confidence as a quality claim:

```bash
cd scanner
uv run aegify benchmark benchmarks/core-v1/sources \
  --ground-truth benchmarks/core-v1/ground-truth.json \
  --min-precision 1.0 \
  --min-recall 1.0 \
  --output-file benchmark-report.json
```

The committed `core-v1` corpus pairs positive and negative controls for five
high-impact taint rules. Its report records the corpus version, source and
manifest SHA-256 digests, evaluated rule IDs, true positives, false positives,
false negatives, per-rule metrics, and exact unmatched evidence identities.
CI currently requires `TP 9 / FP 0 / FN 0`, so precision, recall, and F1 must
all equal `1.0` inside this declared scope. This is a reproducible regression
contract, not a universal accuracy claim for every rule, framework, or program.

For pinned external case labels, use the
[OWASP Python evaluation workflow](/analysis/benchmark-evaluation). It reports
negative cases, separate candidate/blocking metrics, exact-CWE scope, unscored
cases and reproducibility manifests. Public benchmark results and independent
application validation are separate release evidence.

## Proof boundary

AI-generated requests and payloads are templates, not execution results. They
must use placeholders, target an owned or explicitly authorized fixture, remain
non-destructive, and include a negative control. Execution belongs in the
approval-gated HTTP, browser, proxy, or container harness. Runtime observation
and impact proof remain separate evidence states.
