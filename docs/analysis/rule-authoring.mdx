Aegify rules are executable security detectors, not documentation disguised as
configuration. The strict audit gate requires every enabled rule and every
declared pattern to map to implemented evaluator behavior.

## Minimal rule

```yaml
rules:
  - id: AEG-EXAMPLE-001
    name: Untrusted command execution
    description: User-controlled input reaches a process execution API.
    severity: critical
    confidence: 0.9
    languages: [java, kotlin]
    cwe_id: 78
    owasp_category: "A03:2021-Injection"
    patterns:
      - callee_match: "^(exec|start)$"
        receiver_match: "^(Runtime|ProcessBuilder)$"
        args_match: "request|param|input"
        disposition: advisory
    taint:
      source_types: [http_param, http_body]
      sink_types: [os_command]
    defense_patterns:
      - "allowlist"
      - "validateCommand"
    message: Avoid constructing operating-system commands from request data.
```

## Identity and metadata

- Use stable `AEG-<AREA>-<NUMBER>` IDs. Never reuse an ID for a different issue.
- Give rules a concise name, security impact, severity, confidence, CWE, and
  actionable message.
- List only languages supported by the current scanner. A mixed list may include
  deferred languages, but a rule containing only unsupported languages fails.

## Executable patterns

Patterns normalize into either call matching or source matching.

Common call fields:

- `callee` / `callee_match`
- `callee_match_mode: full` for an exact parsed callee; the default uses regex search
- `receiver` / `receiver_match`
- `args_match`, `args_exclude`, and `missing_args`
- `args_match_index` to inspect one zero-based argument rather than every argument together
- `boolean_option` to select a literal keyword or object option and retain unknown values
- language restrictions

Common source fields:

- `pattern_type: regex|negative_check|sequence|taint|entropy`
- `match` / `pattern` / `regex_match`
- `annotation_match`, `decorator_match`, `import_match`
- `assignment_match`, `config_match`, `content_match`
- `file_match`, `must_contain`, `missing_pattern`, and exclusion fields

Compatibility fields are accepted only when `PatternSpec` implements them. A
partially executable rule is still invalid: strict audit reports each
non-executable pattern even if another pattern in the same rule works.

Pattern results default to `candidate` evidence with an `advisory` disposition.
This preserves broad coverage in console, SARIF, GitHub review annotations, and
the dashboard without failing CI. Do not mark a lexical fallback `blocking`.

Source aliases such as `assignment_match` are regular expressions over the
selected source segment. A separate `value_match` is evaluated over that same
segment, so two unrelated statements can satisfy the pair. For a literal
configuration value, bind the identifier, assignment separator and value in one
bounded expression. For API arguments, prefer a parsed call, an exact callee
pattern and constraints on that call's arguments. Test an unrelated identifier,
the same keyword on another line, and a matching keyword in a different argument.

### Hash algorithm selection

`AEG-A02-002` and `AEG-A02-003` separate named MD5/SHA-1 constructors from
algorithm-selecting factories. A factory must match the complete parsed callee
and select an MD5/SHA-1 literal in its first argument. An algorithm name inside
data, options, another function name or model metadata is not that selection.
This follows the argument contracts of
[Node crypto](https://nodejs.org/api/crypto.html#cryptocreatehashalgorithm-options),
[Python hashlib](https://docs.python.org/3/library/hashlib.html), and
[Java MessageDigest](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/security/MessageDigest.html).
Direct constructors, including zero-argument
[Go md5.New](https://pkg.go.dev/crypto/md5#New), are checked separately.

Fixtures cover explicit parsed call forms in Python, JavaScript, TypeScript, Java,
Go, Rust, Swift and Kotlin. These are syntax/selection checks, not library runtime
compatibility tests. Dynamic algorithms, wrappers, aliases and shadowed names
still need symbol/value resolution and human review. A missing literal match
does not establish safe cryptography. Candidates ask whether the resolved API is
used for a security purpose; they do not treat every checksum or HMAC use as a
confirmed vulnerability.

### Boolean options and cookie review

Use a structural option selector when a boolean belongs to one call argument.
An unrelated string, nested object or different argument cannot satisfy it:

```yaml
patterns:
  - callee: '(?-i:(?:res|response)\.cookie)'
    callee_match_mode: full
    languages: [javascript, typescript]
    boolean_option:
      name: secure
      location: argument
      argument: 2
      states: ["false", "missing", "unknown"]
message: "Review cookie Secure option; parsed state: {option_state}."
```

`name` is case sensitive. `location: argument` selects a zero-based index from
0 to 127. `argument: all` checks each positional object, for APIs that accept
variadic objects; its combined state prioritizes `false`, then `missing`, then
`unknown`, and is `true` only when every object has a literal true value.
`location: keyword` selects a Python keyword and forbids an argument index.
Quote the state names so YAML does not convert them to booleans.

| State | Meaning |
|---|---|
| `true` / `false` | The selected syntax contains that boolean literal |
| `missing` | A supported argument list or object lacks the selected option |
| `unknown` | A value, spread, key, syntax form or available parser fact cannot establish it |

Supported facts cover Python keyword arguments and literal dictionary unpacking,
JS/TS object arguments (including TSX), and Go keyed composite literals. Literal
object properties preserve source order and overwrites. A later unresolved
spread or computed key invalidates earlier facts; a later explicit property can
establish its own value. Python duplicate keyword bindings remain unknown.
Comments do not shift structural argument indexes. TypeScript `as`, `satisfies`
and non-null wrappers preserve their operand facts.

Extraction bounds each argument/property list to 128 entries plus an unknown
sentinel, and nested literal spread expansion to eight levels. Hitting a bound
does not establish safety. Parser errors, unsupported language facts and legacy
serialized calls also remain unknown. The parser cache identity includes this
extractor. Structural `missing` checks work on zero-argument calls; ordinary
`args_match` constraints still require arguments.

The selector is valid only for call patterns. Strict audit rejects malformed
selectors and unsupported combinations. Existing callee expressions default to
case-insensitive matching; `(?-i:...)` makes the API spelling case sensitive.
Go extraction now also retains raw argument order for existing call/taint users.

`AEG-A05-005` and `AEG-A05-006` use this contract for cookie reviews. Their selected
argument shapes follow [Flask 3.1](https://flask.palletsprojects.com/en/stable/api/#flask.Response.set_cookie),
[Express 4](https://expressjs.com/en/4x/api/response/#res.cookie),
[Puppeteer 25.11](https://pptr.dev/api/puppeteer.browsercontext.setcookie) and
[Go net/http](https://pkg.go.dev/net/http#SetCookie).
The owned fixtures validate syntax selection, not installed-framework execution.
They do not resolve imports, aliases, shadowed API names, variables, Python
positional flag parameters or later object mutation. Generic `Cookie`,
`NewCookie` and `setCookie` names require checking the actual API contract.
Java stateful builders and retained header/configuration heuristics report
`unmodeled`; they do not infer later setter calls. All these findings remain
advisory candidates. An unknown value is not a proved missing flag, and a true
literal alone does not establish that an application handles cookies safely.

### SQL text construction

The built-in `AEG-SQL-002` rule (CWE-89) uses version 1 `QueryExpression`
facts on parsed calls. It selects SQL text before examining how the text was
built. SQL-looking bound data, arithmetic in parameter values, and `%` or `+`
inside fixed SQL literals cannot establish string construction.

| Shape | Selected text | Excluded bound values |
|---|---|---|
| `db.execute(query, values)` | First positional argument | Later arguments |
| `db.execute(sql=query, parameters=values)` | Named `sql`, `query`, `operation` or `statement` argument | Other keywords |
| `db.query({text: query, values})` | Top-level `text` property | `values` and other properties |
| `db.execute({sql: query, args})` | Top-level `sql` property | `args` and other properties |

Positional SQL and bound values follow the separation documented by
[Python sqlite3](https://docs.python.org/3/library/sqlite3.html#how-to-use-placeholders-to-bind-values-in-sql-queries)
and [node-postgres](https://node-postgres.com/features/queries). Keyword and
`sql` object forms are syntax adapters for other wrappers; matching them does
not prove the receiver implements that API. An object containing both `sql`
and `text` is ambiguous and stays unknown.

The detector matches complete method leaf names, including `execute`,
`executemany`, `executescript`, `execute_async`, `executesql`, `query`, `raw`,
`exec`, `prepare`, `$queryRawUnsafe` and `$executeRawUnsafe`. A matching substring
in `querySelector` or `executeHandler` does not select a sink. Receiver binding
still needs review: these common names can belong to unrelated APIs.

Owned source fixtures cover Python string concatenation, f-strings, percent
formatting and `format`/`format_map`; JS/TS concatenation and template strings;
TS `as`, `satisfies`, non-null and TSX syntax; local assignments, reassignments,
branch joins, bounded loop-carried values, literal argument expansion, and
direct object aliases and property writes. Fixed compositions and later literal
overwrites have paired negative cases. The locked parser versions exercised are
tree-sitter 0.26.0, Python and JavaScript grammars 0.25.0, and TypeScript grammar
0.23.2, under Python 3.14. These are parsing checks, not database/framework runtime
compatibility tests.

Facts preserve the selected argument/property, construction operators, local
origin lines and unresolved details across AST serialization. Their states are
`constant`, `constructed` and `unknown` within this model. Constants can represent
multiple literal branch alternatives; they do not assert a unique runtime string
or safe application behavior. Only constructed SQL text produces this rule's
candidate. The finding asks reviewers to establish the database receiver and
input trust before assessing injection impact.

For the standard first-argument SQL sink model, the taint solver also consumes
these facts: a recognized SQL program that is constant, with no uncertainty,
cannot acquire SQL syntax from its bound values. This applies to the first
positional string or its selected `sql`/`text` field. Unknown or missing facts,
ambiguous query objects, dynamic SQL, custom nonzero argument models and other
sink categories retain their existing conservative taint behavior. Facts belong
to each call position, so a constant call cannot suppress a dynamic call on the
same line. This does not resolve general cross-call context or receiver binding
uncertainty, and does not mark other tainted values as sanitized.

The analysis does not execute source or evaluate arbitrary expressions. It bounds
text to 4,096 characters, traversal to 48 levels and 100,000 steps per file,
object fields/identity alternatives to 64, each value merge to 1,024 steps,
and displayed origins to 16 lines. Loops receive one additional carried pass.
Expression budget exhaustion makes affected calls unknown and emits the
`sql_expression_limit` scan gap, so the scan is partial. Origin display truncation
alone does not change a result. The cache fingerprint includes the extractor;
legacy ASTs without these facts must be reparsed, not treated as negatives.

This is bounded local value analysis, not a complete control-flow, type, import,
alias or SQL-grammar analysis. Function returns, global/closure propagation,
nested heap aliases, arbitrary helper calls, tagged SQL templates, sanitizers,
path feasibility and exact exception/loop semantics require further models.
Unknown spreads, computed keys and call effects retain uncertainty where tracked.
Unsupported forms can remain undetected; absence of a finding is not proof of
safety. The rule does not create a taint path or promote candidates to blocking
or runtime-proven evidence.

### OAuth scope review boundary

`AEG-OAUTH-004` recognizes selected OAuth authorization/provider calls with
administrative-looking or wildcard literal scopes, explicitly named OAuth scope
configuration, and OAuth token-exchange handlers without a recognized local
scope check. Fixtures cover Python and JS/TS syntax, string/list values,
validated callbacks and nearby non-OAuth code. Computed scope values and
provider-specific policy need separate review; these patterns do not establish
SDK-version compatibility or end-to-end authorization behavior.

The finding remains a review candidate. A provider may grant fewer scopes than
requested, as described in [RFC 6749 section 3.3](https://www.rfc-editor.org/rfc/rfc6749#section-3.3).
Assess the actual application privileges and provider/library enforcement using
the [OAuth privilege restriction guidance](https://www.rfc-editor.org/rfc/rfc9700#section-2.3).
Scope-name matches and absence of a locally named validator alone do not prove
a vulnerability.

## Evidence and CI disposition

Findings carry two independent fields:

- `evidence_state`: `candidate`, `reachable`, `observed`, or `impact_proven`;
- `disposition`: `advisory` or `blocking`.

Native and YAML pattern matches are advisory by default. A source-to-sink taint
flow is emitted as `reachable` and `blocking`. A structured semantic detector
may also emit a blocking result when its required receiver, ordering, defense,
and scope evidence is satisfied. Severity does not override this contract: a
critical advisory remains visible but does not change the CLI exit code.

SARIF encodes advisory results as `level: note`, `kind: review`, and
`blocksCi: false`. Blocking high or critical results produce a non-zero CLI exit
code. Dashboard ingestion stores and filters both classification fields.

## Structured database-race evidence

The `database_race` semantic detector finds a bounded read-modify-write sequence
inside one parsed function. Broad patterns for the same rule remain advisory.

```yaml
patterns:
  - sequence_match: ["findById", "save"]
    disposition: advisory
semantic:
  kind: database_race
  read_callee: "(findById|findOne|get|load)"
  write_callee: "(save|update|delete)"
  receiver_match: "(?:^|[._])(repo|repository|dao|db)(?:$|[._])"
  required_between: "(?:\\+=|-=|\\+\\+|--)"
  defense_match: "(?:transaction|atomic|lock|compareAndSet)"
  same_receiver: true
  max_lines_between: 20
```

The blocking finding is created only when the read and write use the required
database receiver, occur in order and within the bound, contain the required
business-state operation, and have no matching transaction or concurrency
defense in that function.

## Negative checks

Negative rules require a positive scope anchor. A global “missing header” or
“missing validation” declaration without a file, endpoint, function, or framework
anchor would match everything and is rejected. Use a bounded form:

```yaml
- pattern_type: negative_check
  match: "@PostMapping|router.post"
  must_contain: "authorize|requireRole"
  scope: function
```

If a safe implementation does not exist, remove the pattern or mark the entire
reference rule `enabled: false` with a concrete `disabled_reason`.

## Taint rules

Top-level `taint` filters flows already recognized by scanner source, sink and
propagation models. It does not install a new model or create a flow from text.

| Field | Meaning |
|---|---|
| `source_types` | Exact source category names, such as `http_param` |
| `sink_types` | Exact sink category names, such as `sql_query` |
| `source_pattern` | Python regex search over the source variable |
| `sink_pattern` | Python regex search over the sink function |
| `ignore_sanitizers` | Boolean; defaults to `false`, which omits sanitized flows |

Selectors combine as filters. Type lists may contain at most 100 nonempty names
of at most 256 characters each; patterns are limited to 4,096 characters. At least
one nonempty selector is required. Regex matching uses Python's case-insensitive
mode; inline flags can refine it. An empty mapping, malformed regex, non-boolean
sanitizer option or unsupported field fails audit and rule loading.

**Migration:** `sources`, `sinks` and `propagation` are not executable fields in
this mapping. Previously they could be silently ignored. Use `source_types` /
`sink_types` and the supported pattern fields for flow selection. Move descriptive
propagation lists into comments; changing propagation behavior requires scanner
model work and tests. The bundled migration only comments out unused propagation
notes; its existing selectors and detection patterns are unchanged.

Ordinary, selected-file and workspace scans also audit configured custom rules.
Invalid, empty, missing or partially loaded custom rule sets add the
`custom_rule_load_failed` analysis gap. Remaining findings are retained, but the
scan is `partial` and exits `3`; a skipped custom rule cannot produce a clean CI
result. Run `audit-rules --strict` for the detailed rule diagnostics.

Preserve the path, source, sink, sanitizer decision, call context and module
identity in evidence. Avoid broad categories that cannot be tested with positive
and negative fixtures. The dashboard checks this field structure; Python regex
compilation and detector behavior are verified by the scanner.

## Run rule fixtures

`test-rule` runs one submitted YAML rule through the actual parser, call graph,
taint analysis and detector. Built-in and other custom rules are excluded. Use it
while authoring and as a CI regression gate:

```bash
cd scanner
uv run aegify test-rule examples/rule-fixtures/call.yml \
  --fixtures examples/rule-fixtures/call.fixtures.json \
  --output-file /tmp/call-fixture-report.json

uv run aegify test-rule examples/rule-fixtures/taint.yml \
  --fixtures examples/rule-fixtures/taint.fixtures.json --json
```

Copy these examples for a new rule. The call example includes a request argument,
a constant, a different callee and a different argument position. The taint
example includes direct and cross-file request-to-SQL flows, a constant query and
a parameterized query. These are owned static fixtures; neither the application nor
the database is executed.

Each JSON suite declares `schema_version: 1`, a stable `suite_id`, semantic
`suite_version`, one `rule_id`, and `cases`. Each case has a unique `id`, a list of
`files` with `path` and UTF-8 `content`, and an `expected` list:

```json
{
  "id": "request-argument",
  "files": [{
    "path": "main.py",
    "content": "def handle(request):\n    return review_target(request)\n"
  }],
  "expected": [{
    "rule_id": "AEG-CUSTOM-001",
    "file_path": "main.py",
    "line_start": 2
  }]
}
```

An empty `expected` list is a negative case. A passing suite requires at least one
positive case and two negative cases. Every finding must match the expected rule,
relative path and exact starting line; there is no line tolerance. Missing and
unexpected findings fail the gate. Several files in one case share the same
analysis context. Separate cases have fresh sources, storage and engine state.

Reports contain actual evidence states, CI dispositions and available taint paths,
but these fields are displayed rather than asserted by this location-only fixture
schema. Add scanner tests when changing evidence classification or flow semantics.
Fixtures cover their submitted inputs; a pass does not establish library runtime
compatibility, all declared languages, application-wide security, or general
precision/recall. Use the [evaluation protocol](/analysis/benchmark-evaluation)
for broader quality claims.

| Exit | Meaning |
|---:|---|
| `0` | All cases matched and the control requirement was met |
| `1` | Complete analysis with missing or unexpected findings |
| `2` | Invalid input/rule, worker failure, deadline, output limit or report-write failure |
| `3` | Incomplete analysis or insufficient positive/negative controls |

Unsupported source, syntax recovery, missing rule evaluation and analysis limits
cannot pass as negative cases. Reaching a YAML detector's internal finding cap
is conservatively incomplete, even if the last emitted finding matched an
expectation. Split broad fixtures into smaller cases when appropriate. Metrics
are `null` for incomplete analysis; ratios with empty denominators are also `null`.
There is no line-based accuracy or true-negative count inferred from the source.

### Bounds and replay

Suites allow 20 cases, 12 files per case, 100 expectations per case, 64 KiB per
source file and 1 MiB of source in total. Paths use ASCII letters, digits,
underscores, hyphens, dots and slashes, with no absolute/dot/hidden segments,
case collisions or file/directory collisions. Input files must be regular files,
not symlinks or FIFOs. Rule YAML is limited to 128 KiB and 100 patterns; aliases,
duplicate mapping keys and excessive nesting are rejected. The suite JSON limit
is 2 MiB and the report limit is 4 MiB.

The parent enforces a whole-suite wall deadline (`--timeout-seconds`, default 30,
range 1–120) and stops the worker process group when it exits or reaches a limit.
Linux workers also lower address-space limits to at most 2 GiB. macOS reports no
address-space limit. The subprocess uses a minimal environment, fixed memory
storage, no AI, and no target configuration, imports, installs or build commands.
This process boundary is not an OS security sandbox; run untrusted submissions in
an isolated worker/container with egress and resource limits. The container CI
gate uses a read-only, unprivileged, network-disabled scanner image.

The manifest records exact rule bytes, canonical suite/source digests, scanner
implementation and rules, parser fingerprint, Python/package version, effective
configuration and worker limits. `result_digest` hashes inputs and normalized
results while excluding per-case runtime duration. Compare it across fresh
processes with the same implementation and environment. It is an integrity and
replay aid, not a signature or independent truth label.

## Evaluate in the project Rule lab

Open a project and choose **Rule lab**. A project maintainer can load the call
selector or taint example, edit the YAML, and add cases, files and expected
locations. The **Suite JSON** tab accepts the same version 1 input as the CLI.
Select **Run evaluation** to queue the saved input on the source worker.

The result shows matched, unexpected and missed locations, parser gaps, fixture
precision/recall, static source-to-sink paths and the reproducibility manifest.
Incomplete analysis has no aggregate precision/recall. Location assertions do
not assert the displayed taint path or prove runtime impact. The draft may change
while an earlier result remains selected; the screen identifies that result as
belonging to its saved input.

Project viewers can read reports and job logs. Maintainers can cancel, load saved
input or rerun it. Testing a draft does not publish it to global rule management.
The lab invokes the installed Python fixture worker with one rule, without AI,
repository credentials, application execution or builds. An old worker without
fixture support is shown as unavailable; upgrade the worker with the dashboard.

**Export rule** and **Export fixtures** produce inputs for the same CI command:

```bash
aegify test-rule rule.yml --fixtures fixtures.json --timeout-seconds 30 --json
```

The dashboard has a fixed 30-second execution budget, one active evaluation per
project, 10 new jobs per user per hour, 25 unexpired jobs per project and 16 active
jobs per installation. It shows the latest 25 jobs. A source scan already running
can delay a fixture job; the shared worker alternates queue preference between
completed jobs. The other fixture size limits above apply unchanged.

Inputs and full reports are encrypted with the installation key and expire seven
days after enqueue. The API stops returning them at expiry even before the worker's
hourly cleanup. Status, fixed job messages, audit records and digests remain.
The report-byte digest includes timing; the report's `result_digest` excludes
case duration for same-environment comparison. Neither digest is a signature.
Whole-second timeouts use an integer in new report manifests, so JSON inputs
containing `30` and `30.0` retain the same replay identity. The downloaded report
can be parsed as a `FixtureReport` and checked with `result_digest`; the digest
algorithm is unchanged and previously saved reports are not rewritten.
Backups have their own retention policy and may contain earlier encrypted records.

Cancellation fences publication immediately and stops computation at the next
five-second heartbeat. Project/account revocation and archival are rechecked on
claim, heartbeat and publication. Interrupted workers can recover the same input
up to three attempts. Backup restoration cancels active fixture jobs; a maintainer
must explicitly rerun them after reviewing the restored access and input.

## Defense patterns

Defense patterns reduce confidence or suppress a finding only when their scope
and meaning are clear. Do not use generic words such as `safe` or `secure`.
Prefer concrete validators, framework guards, parameterization APIs, or encoding
functions, and include bypass-oriented negative tests.

## Strict audit

Run:

```bash
cd scanner
uv run aegify audit-rules ../rules --strict
```

The audit rejects:

- invalid YAML and regular expressions;
- missing or duplicate IDs;
- invalid severity;
- unknown fields;
- unsupported-only language declarations;
- enabled rules with no executable detector;
- any individual non-executable pattern.

The release baseline is 311 definitions, 303 enabled/executable rules, 8
explicitly disabled reference rules, and 986/986 enabled patterns executable.

## Test requirements

Every new or materially changed rule should include:

1. a minimal positive fixture;
2. a safe negative fixture;
3. a cross-file or framework fixture when claimed;
4. stable rule ID, severity, location, and evidence assertions;
5. a test proving a nearby decoy is not selected.

Rules with a fallback and a semantic detector also require assertions that the
fallback is retained as advisory, the semantic path is blocking, and a defended
or unrelated path is not blocking.

Rules affecting reachability should test repository/module identity and ambiguous
targets. Rules affecting secrets or logs must use synthetic placeholders.
