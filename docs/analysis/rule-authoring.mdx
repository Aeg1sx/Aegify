Aegify rules are executable security detectors, not documentation disguised as
configuration. The strict audit gate requires every enabled rule and every
declared pattern to map to implemented evaluator behavior.

## Minimal rule

```yaml
rules:
  - id: AEG-EXAMPLE-001
    name: Untrusted command execution
    description: User-controlled input reaches a process execution API.
    severity: critical
    confidence: 0.9
    languages: [java, kotlin]
    cwe_id: 78
    owasp_category: "A03:2021-Injection"
    patterns:
      - callee_match: "^(exec|start)$"
        receiver_match: "^(Runtime|ProcessBuilder)$"
        args_match: "request|param|input"
        disposition: advisory
    taint:
      source_types: [http_param, http_body]
      sink_types: [os_command]
    defense_patterns:
      - "allowlist"
      - "validateCommand"
    message: Avoid constructing operating-system commands from request data.
```

## Identity and metadata

- Use stable `AEG-<AREA>-<NUMBER>` IDs. Never reuse an ID for a different issue.
- Give rules a concise name, security impact, severity, confidence, CWE, and
  actionable message.
- List only languages supported by the current scanner. A mixed list may include
  deferred languages, but a rule containing only unsupported languages fails.

## Executable patterns

Patterns normalize into either call matching or source matching.

Common call fields:

- `callee` / `callee_match`
- `callee_match_mode: full` for an exact parsed callee; the default uses regex search
- `receiver` / `receiver_match`
- `args_match`, `args_exclude`, and `missing_args`
- `args_match_index` to inspect one zero-based argument rather than every argument together
- `boolean_option` to select a literal keyword or object option and retain unknown values
- language restrictions

Common source fields:

- `pattern_type: regex|negative_check|sequence|taint|entropy`
- `match` / `pattern` / `regex_match`
- `annotation_match`, `decorator_match`, `import_match`
- `assignment_match`, `config_match`, `content_match`
- `file_match`, `must_contain`, `missing_pattern`, and exclusion fields

Compatibility fields are accepted only when `PatternSpec` implements them. A
partially executable rule is still invalid: strict audit reports each
non-executable pattern even if another pattern in the same rule works.

Pattern results default to `candidate` evidence with an `advisory` disposition.
This preserves broad coverage in console, SARIF, GitHub review annotations, and
the dashboard without failing CI. Do not mark a lexical fallback `blocking`.

Source aliases such as `assignment_match` are regular expressions over the
selected source segment. A separate `value_match` is evaluated over that same
segment, so two unrelated statements can satisfy the pair. For a literal
configuration value, bind the identifier, assignment separator and value in one
bounded expression. For API arguments, prefer a parsed call, an exact callee
pattern and constraints on that call's arguments. Test an unrelated identifier,
the same keyword on another line, and a matching keyword in a different argument.

### Hash algorithm selection

`AEG-A02-002` and `AEG-A02-003` separate named MD5/SHA-1 constructors from
algorithm-selecting factories. A factory must match the complete parsed callee
and select an MD5/SHA-1 literal in its first argument. An algorithm name inside
data, options, another function name or model metadata is not that selection.
This follows the argument contracts of
[Node crypto](https://nodejs.org/api/crypto.html#cryptocreatehashalgorithm-options),
[Python hashlib](https://docs.python.org/3/library/hashlib.html), and
[Java MessageDigest](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/security/MessageDigest.html).
Direct constructors, including zero-argument
[Go md5.New](https://pkg.go.dev/crypto/md5#New), are checked separately.

Fixtures cover explicit parsed call forms in Python, JavaScript, TypeScript, Java,
Go, Rust, Swift and Kotlin. These are syntax/selection checks, not library runtime
compatibility tests. Dynamic algorithms, wrappers, aliases and shadowed names
still need symbol/value resolution and human review. A missing literal match
does not establish safe cryptography. Candidates ask whether the resolved API is
used for a security purpose; they do not treat every checksum or HMAC use as a
confirmed vulnerability.

### Boolean options and cookie review

Use a structural option selector when a boolean belongs to one call argument.
An unrelated string, nested object or different argument cannot satisfy it:

```yaml
patterns:
  - callee: '(?-i:(?:res|response)\.cookie)'
    callee_match_mode: full
    languages: [javascript, typescript]
    boolean_option:
      name: secure
      location: argument
      argument: 2
      states: ["false", "missing", "unknown"]
message: "Review cookie Secure option; parsed state: {option_state}."
```

`name` is case sensitive. `location: argument` selects a zero-based index from
0 to 127. `argument: all` checks each positional object, for APIs that accept
variadic objects; its combined state prioritizes `false`, then `missing`, then
`unknown`, and is `true` only when every object has a literal true value.
`location: keyword` selects a Python keyword and forbids an argument index.
Quote the state names so YAML does not convert them to booleans.

| State | Meaning |
|---|---|
| `true` / `false` | The selected syntax contains that boolean literal |
| `missing` | A supported argument list or object lacks the selected option |
| `unknown` | A value, spread, key, syntax form or available parser fact cannot establish it |

Supported facts cover Python keyword arguments and literal dictionary unpacking,
JS/TS object arguments (including TSX), and Go keyed composite literals. Literal
object properties preserve source order and overwrites. A later unresolved
spread or computed key invalidates earlier facts; a later explicit property can
establish its own value. Python duplicate keyword bindings remain unknown.
Comments do not shift structural argument indexes. TypeScript `as`, `satisfies`
and non-null wrappers preserve their operand facts.

Extraction bounds each argument/property list to 128 entries plus an unknown
sentinel, and nested literal spread expansion to eight levels. Hitting a bound
does not establish safety. Parser errors, unsupported language facts and legacy
serialized calls also remain unknown. The parser cache identity includes this
extractor. Structural `missing` checks work on zero-argument calls; ordinary
`args_match` constraints still require arguments.

The selector is valid only for call patterns. Strict audit rejects malformed
selectors and unsupported combinations. Existing callee expressions default to
case-insensitive matching; `(?-i:...)` makes the API spelling case sensitive.
Go extraction now also retains raw argument order for existing call/taint users.

`AEG-A05-005` and `AEG-A05-006` use this contract for cookie reviews. Their selected
argument shapes follow [Flask 3.1](https://flask.palletsprojects.com/en/stable/api/#flask.Response.set_cookie),
[Express 4](https://expressjs.com/en/4x/api/response/#res.cookie),
[Puppeteer 25.11](https://pptr.dev/api/puppeteer.browsercontext.setcookie) and
[Go net/http](https://pkg.go.dev/net/http#SetCookie).
The owned fixtures validate syntax selection, not installed-framework execution.
They do not resolve imports, aliases, shadowed API names, variables, Python
positional flag parameters or later object mutation. Generic `Cookie`,
`NewCookie` and `setCookie` names require checking the actual API contract.
Java stateful builders and retained header/configuration heuristics report
`unmodeled`; they do not infer later setter calls. All these findings remain
advisory candidates. An unknown value is not a proved missing flag, and a true
literal alone does not establish that an application handles cookies safely.

### OAuth scope review boundary

`AEG-OAUTH-004` recognizes selected OAuth authorization/provider calls with
administrative-looking or wildcard literal scopes, explicitly named OAuth scope
configuration, and OAuth token-exchange handlers without a recognized local
scope check. Fixtures cover Python and JS/TS syntax, string/list values,
validated callbacks and nearby non-OAuth code. Computed scope values and
provider-specific policy need separate review; these patterns do not establish
SDK-version compatibility or end-to-end authorization behavior.

The finding remains a review candidate. A provider may grant fewer scopes than
requested, as described in [RFC 6749 section 3.3](https://www.rfc-editor.org/rfc/rfc6749#section-3.3).
Assess the actual application privileges and provider/library enforcement using
the [OAuth privilege restriction guidance](https://www.rfc-editor.org/rfc/rfc9700#section-2.3).
Scope-name matches and absence of a locally named validator alone do not prove
a vulnerability.

## Evidence and CI disposition

Findings carry two independent fields:

- `evidence_state`: `candidate`, `reachable`, `observed`, or `impact_proven`;
- `disposition`: `advisory` or `blocking`.

Native and YAML pattern matches are advisory by default. A source-to-sink taint
flow is emitted as `reachable` and `blocking`. A structured semantic detector
may also emit a blocking result when its required receiver, ordering, defense,
and scope evidence is satisfied. Severity does not override this contract: a
critical advisory remains visible but does not change the CLI exit code.

SARIF encodes advisory results as `level: note`, `kind: review`, and
`blocksCi: false`. Blocking high or critical results produce a non-zero CLI exit
code. Dashboard ingestion stores and filters both classification fields.

## Structured database-race evidence

The `database_race` semantic detector finds a bounded read-modify-write sequence
inside one parsed function. Broad patterns for the same rule remain advisory.

```yaml
patterns:
  - sequence_match: ["findById", "save"]
    disposition: advisory
semantic:
  kind: database_race
  read_callee: "(findById|findOne|get|load)"
  write_callee: "(save|update|delete)"
  receiver_match: "(?:^|[._])(repo|repository|dao|db)(?:$|[._])"
  required_between: "(?:\\+=|-=|\\+\\+|--)"
  defense_match: "(?:transaction|atomic|lock|compareAndSet)"
  same_receiver: true
  max_lines_between: 20
```

The blocking finding is created only when the read and write use the required
database receiver, occur in order and within the bound, contain the required
business-state operation, and have no matching transaction or concurrency
defense in that function.

## Negative checks

Negative rules require a positive scope anchor. A global “missing header” or
“missing validation” declaration without a file, endpoint, function, or framework
anchor would match everything and is rejected. Use a bounded form:

```yaml
- pattern_type: negative_check
  match: "@PostMapping|router.post"
  must_contain: "authorize|requireRole"
  scope: function
```

If a safe implementation does not exist, remove the pattern or mark the entire
reference rule `enabled: false` with a concrete `disabled_reason`.

## Taint rules

Taint rules declare compatible source and sink categories and may select library
model behavior. They must preserve the path, source, sink, sanitizer decision,
call context, and repository/module identity in evidence. Avoid broad categories
that cannot be tested with positive and negative fixtures.

## Defense patterns

Defense patterns reduce confidence or suppress a finding only when their scope
and meaning are clear. Do not use generic words such as `safe` or `secure`.
Prefer concrete validators, framework guards, parameterization APIs, or encoding
functions, and include bypass-oriented negative tests.

## Strict audit

Run:

```bash
cd scanner
uv run aegify audit-rules ../rules --strict
```

The audit rejects:

- invalid YAML and regular expressions;
- missing or duplicate IDs;
- invalid severity;
- unknown fields;
- unsupported-only language declarations;
- enabled rules with no executable detector;
- any individual non-executable pattern.

The release baseline is 311 definitions, 303 enabled/executable rules, 8
explicitly disabled reference rules, and 986/986 enabled patterns executable.

## Test requirements

Every new or materially changed rule should include:

1. a minimal positive fixture;
2. a safe negative fixture;
3. a cross-file or framework fixture when claimed;
4. stable rule ID, severity, location, and evidence assertions;
5. a test proving a nearby decoy is not selected.

Rules with a fallback and a semantic detector also require assertions that the
fallback is retained as advisory, the semantic path is blocking, and a defended
or unrelated path is not blocking.

Rules affecting reachability should test repository/module identity and ambiguous
targets. Rules affecting secrets or logs must use synthetic placeholders.
