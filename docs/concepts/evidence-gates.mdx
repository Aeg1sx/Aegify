title: "Evidence states and CI gates"
description: "Keep evidence strength independent from severity and CI-blocking disposition."

---

Aegify records what an analyzer knows separately from what repository policy
does with that evidence. This prevents a broad lexical signal from being
presented as a proven, reachable vulnerability.

## Evidence states

| State | Required evidence |
|---|---|
| `candidate` | A static rule or imported tool identified a review target |
| `reachable` | A bounded graph or taint path connects a supported source and sink |
| `observed` | Approved runtime evidence exercised the route or code path |
| `impact_proven` | A separate, approved proof demonstrated security impact |

Evidence states are monotonic descriptions of retained evidence, not confidence
labels generated by severity.

## Gate disposition

- `advisory` results remain visible in console, SARIF, GitHub annotations, and
  the dashboard, but do not fail CI.
- `blocking` results can fail CI when their severity meets the configured
  threshold.

Native and YAML lexical patterns default to `candidate/advisory`. Taint paths
and structured semantic detectors may emit `reachable/blocking` only when their
required evidence is satisfied.

## Examples of blocking evidence

- an HTTP parameter reaches a modeled SQL, command, SSRF, or template sink;
- a database receiver performs an ordered read-modify-write sequence without a
  supported transaction, lock, or atomic defense;
- an untrusted format program reaches a receiver-format sink;
- validation and sanitizer state is tracked on the actual source-to-sink path.

<Warning>
  `calledByFrontend=false`, `exposedViaGateway=false`, and an unresolved target
  mean that no supported static linkage was found in the supplied evidence.
  They do not prove that the code is unreachable at runtime.
</Warning>
