Aegify records what an analyzer knows separately from what repository policy
does with that evidence. This prevents a broad lexical signal from being
presented as a proven, reachable vulnerability.

## Evidence states

| State | Required evidence |
|---|---|
| `candidate` | A static rule or imported tool identified a review target |
| `reachable` | A bounded graph or taint path connects a supported source and sink |
| `observed` | Approved runtime evidence exercised the route or code path |
| `impact_proven` | A separate, approved proof demonstrated security impact |

Evidence states are monotonic descriptions of retained evidence, not confidence
labels generated by severity.

## Gate disposition

Analysis health is separate from finding severity. A failed or partial scan must
never be interpreted as a clean scan, including when it contains zero findings.

| CLI exit | Meaning |
|---|---|
| `0` | Analysis completed with no blocking high/critical findings |
| `1` | Analysis completed and found a blocking high/critical finding |
| `2` | Analysis failed, or input/configuration was invalid |
| `3` | Analysis was partial: inspect the reported coverage gaps |

These codes apply to `scan`, `scan-pr`, and `scan-workspace`. A benchmark also
fails its metric gate when precision or recall is below the requested threshold;
perfect metrics from a partial scan cannot pass the gate.

SARIF retains `analysisStatus`, `analysisGaps`, `analysisScope`, `evaluatedRules`,
`analyzedFiles`, and bounded `parseDiagnostics` in run properties. Syntax recovery,
unreadable sources, file-size limits, and result/analysis bounds are visible gaps.
`max_file_size_kb`, `max_findings_per_rule`, and `max_findings_per_file` accept `0`
to disable that bound; do this only after considering the available worker memory.

Global taint limits are configurable under `taint`: `max_contexts` (default
10,000), `context_depth` (default 2, range 1–4), and `max_iterations` (default 64).
Increasing a bound can increase memory and latency. A reached bound still marks
the scan partial; changing a limit never hides the corresponding coverage gap.

The dashboard reconciles absent findings only after a completed import on the
project's explicitly supplied default branch, and only for analyzed file paths
and evaluated rules. Partial scans, feature branches, excluded files, disabled
rules and legacy reports without scope cannot establish absence. Files removed
from the source tree remain unresolved until their deletion is reviewed. Import
failure rolls back absence reconciliation.

### File paths in SARIF

New Aegify reports mark `artifactPathEncoding=percent-encoded-path-v1` in run
properties. Primary and code-flow `artifactLocation.uri` values encode UTF-8
file-path characters such as spaces, brackets, `#`, `?`, and literal `%`. A
`%WORKDIR%` base records the report generator's working directory. The source
inventory, provenance, call graph, and fingerprints retain their original paths.

The dashboard decodes this marked format exactly once before matching source
identities and importing flow locations. Unmarked legacy reports retain their
literal paths; `%2F` in an old filename is not interpreted as a separator.
Malformed marked encodings, unsupported encoding versions, and an imported code
flow above 10,000 locations are rejected before publication. Keep scanner and dashboard
versions aligned: upgrade the dashboard before importing reports from a newer
scanner. Older dashboards do not understand the encoding marker.

This contract preserves the scanner's path syntax. It does not rebase paths to
another checkout, normalize Windows paths on a Unix host, or change generic
third-party SARIF URI handling. GitHub's [SARIF guidance](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support)
describes source-root and relative URI requirements for other producers.

## Finding disposition

- `advisory` results remain visible in console, SARIF, GitHub annotations, and
  the dashboard, but do not fail CI.
- `blocking` results can fail CI when their severity meets the configured
  threshold.

Native and YAML lexical patterns default to `candidate/advisory`. Taint paths
and structured semantic detectors may emit `reachable/blocking` only when their
required evidence is satisfied.

## Examples of blocking evidence

- an HTTP parameter reaches a modeled SQL, command, SSRF, or template sink;
- a database receiver performs an ordered read-modify-write sequence without a
  supported transaction, lock, or atomic defense;
- an untrusted format program reaches a receiver-format sink;
- validation and sanitizer state is tracked on the actual source-to-sink path.

<Warning>
  `calledByFrontend=false`, `exposedViaGateway=false`, and an unresolved target
  mean that no supported static linkage was found in the supplied evidence.
  They do not prove that the code is unreachable at runtime.
</Warning>
