Each endpoint record connects the route to its handler, related findings and available observations.

```text
frontend call
  -> public Gateway route
  -> path transformation
  -> backend endpoint
  -> finding
  -> optional runtime observation
```

## Review endpoint records

Open **Endpoints** to review the method, path, handler, source location and recorded evidence together. A route can have frontend, gateway and runtime records. The header counts each route with linked evidence once. An authentication signal indicates a pattern found in the scanned source. Confirm enforcement in the application.

Search by path, handler, source file, repository or framework. **Filters** narrows the list by method, framework, authentication signal or kind of evidence. **Include all scan records** also shows repeated observations, assets and internal routes. **By file** groups records by repository and source. Opening a record and using the browser's Back button restores the search and filters.

## Frontend calls

Supported extraction recognizes bounded `fetch` and axios-style requests,
including common literal and template construction. Each call retains file,
line, method, path, and confidence.

## Spring Cloud Gateway

Gateway YAML and supported Java/Kotlin DSL routes contribute host, path, and
method predicates. Aegify applies supported transformations such as
`StripPrefix`, `RewritePath`, `PrefixPath`, and `SetPath` before matching the
downstream controller.

## Backend endpoints

Endpoint extraction covers the complete declared language matrix:

| Language | Framework families |
| --- | --- |
| Python | Flask, FastAPI, Django |
| JavaScript | Express |
| TypeScript | Express, NestJS, Next.js App Router |
| Java | Spring MVC/WebFlux |
| Go | net/http, Gin, Echo, Fiber, Chi, Gorilla |
| Rust | Actix Web, Axum, Rocket |
| Swift | Vapor, Hummingbird |
| Kotlin | Spring MVC/WebFlux, Ktor |

Spring extraction combines class and method mappings, HTTP methods, named
`path` and `value` attributes, and Kotlin handlers. Registration-style routers
retain the declared handler when it can be resolved, so the endpoint can become
an entry point in the call graph. Django paths are normalized before quality
filtering, and Next.js App Router paths are derived from `app/**/route` files.

The scanner test suite exercises every language/framework pair in this table.
This is 100% coverage of the declared matrix, not a claim that arbitrary runtime
registrations, generated routes, custom wrappers, or every third-party web
framework can be recovered statically.

## Runtime evidence

Approved HTTP, browser, proxy, HAR, and OpenTelemetry observations may attach to
the same route. Observation changes the evidence record, but does not
automatically establish exploit impact.

<Note>
  Dynamic URL construction, runtime route registration, custom Gateway filters,
  and unresolved framework behavior can remain unlinked. The absence of a link
  is reported as an evidence limit, not as proof that the surface is safe.
</Note>

See [external and runtime adapters](/integrations/external-runtime-adapters) and
the [verification harness](/verification/harness) for supported evidence
formats and execution controls.
