## Start the team installation

Configure the [authentication allowlist and workspace administrators](/operations/authentication)
and configure [encrypted backups and separate key custody](/operations/backup-recovery).
From the repository root:

```bash
docker compose up -d --build dashboard worker ai-worker
docker compose ps
docker compose logs --tail=100 worker ai-worker
```

The dashboard applies migrations and enables SQLite WAL before it becomes healthy. The worker then starts
with the same local SQLite volume, admission configuration and encryption key.
Both containers use UID 1001 for the data volume. This deployment is a single-host
team installation; do not place SQLite on an NFS share or treat it as a multi-host
database service.

Readers and the worker share WAL snapshots; lock contention retries the entire
rolled-back write transaction up to four times with jitter. A failed retry remains
an error. See [SQLite's isolation contract](https://www.sqlite.org/isolation.html).
Use the [operator backup CLI](/operations/backup-recovery), which captures a
consistent live snapshot, or stop the dashboard and both workers before copying database files.
Copying only the live `.db` file can omit committed WAL data.

The worker image pins its Python, Node and uv base images. Its build context is an
explicit allowlist excluding local credentials, databases and reports. It runs as
a non-root user with a read-only root filesystem, a temporary workspace, no added
capabilities, a two-CPU/two-GiB limit and a 128-process limit.

The separate `ai-worker` service uses the same trusted image and database, with a
one-CPU/one-GiB limit and a 64-process limit. Each service has its own heartbeat.
AI calls cannot occupy the source scanner's job loop. No model is called until
an admitted project maintainer explicitly queues a review and AI settings are enabled.

## Upgrade an existing installation

Back up and verify the current database first. Stop `worker`, `ai-worker` (if
already installed), and `dashboard` before applying this upgrade. The old web
process must be stopped: its request-lifetime AI tasks do not understand leases.
Migration `20260924060000_durable_ai_reviews` marks unfinished legacy AI jobs as
failed and retains their history. It cannot infer their requester or provider
outcome, so it never resumes them. Start all three services after the migration.

Migration `20260924070000_ai_review_history` adds retained review records. Stop
the web process and AI worker together before applying it, then run matching
versions. Older jobs keep an explicit legacy history marker; existing mutable
finding contents are not copied into invented historical records. An interrupted
durable job may resume under its existing lease/recovery rules, but any missing
output from batches completed before this upgrade remains unavailable.

Migration `20260924090000_schema_parity` corrects the database default for a new
rule's `updatedAt`. It copies the Rule table in a transaction, preserving every
stored value, including legacy epoch timestamps and custom rule contents. It
does not estimate missing historical dates. Allow temporary space for a second
copy of the Rule table while the services are stopped.

The Prisma ownership relation now explicitly matches the existing database:
a user referenced by `Project.userId` cannot be deleted until that ownership is
transferred or removed. This does not change project memberships or admission
policy. The migration does not rebuild the Project table.

CI deploys the migration history to a fresh database and compares it with the
declared Prisma schema. It also upgrades an owned, populated previous-version
database, checks retained access and evidence, and injects a statement failure
after the old Rule table is dropped to verify transaction rollback. Run that
isolated regression locally after generating the Prisma client:

```bash
cd dashboard
npm run test:migrations
```

The regression creates and removes private temporary databases; it does not use
the installation's `DATABASE_URL`. Schema comparison covers Prisma-supported
objects; separate assertions check SQLite integrity, foreign keys, the membership
role constraint and the saved-review update trigger. A failed migration keeps
startup blocked. Inspect its error and migration history against the verified
backup before an operator chooses a recovery action; restarting alone does not
clear a failed migration record.

## Durable AI finding reviews

Open **LLM Security Review**, choose a project scan and select **Quick Review** or
**Deep Analysis**. Completed and partial static scans are eligible; review does
not upgrade a partial scan's coverage. Deep mode supplies a bounded graph context.
This screen reviews a fixed snapshot of existing findings; the scanner's separate
source-tool agent is described in [AI SAST operations](/analysis/ai-sast-operations).

Both `POST /api/llm-jobs` and the compatible `POST /api/llm-scan` return `202` after
storing a job. The web process never dispatches these review calls. Inputs are
sanitized, hashed and encrypted, with the requester, project, provider, model,
prompt version and configuration identity fixed at enqueue time. Published
suggestions link the job, batch, source evidence, prompt and response digests.
API job metadata omits encrypted input, credentials and lease tokens.

The AI worker rechecks admission, membership, project archival, scan binding,
provider configuration and source identity before dispatch and publication.
Its two-minute lease is renewed every ten seconds. Cancellation fences publication
immediately and aborts the local request on the next heartbeat. An already sent
request may still incur charges. Human finding status, owner, priority, ticket
and accepted/rejected AI decisions are preserved.

Local work can recover up to three times. A provider call is recorded **before**
dispatch. If the worker stops without storing a receipt, that call becomes
`unknown` and the job stops without an automatic retry. Completed batches survive
a restart; the next undispatched batch can continue. This avoids automatic paid
replays but cannot guarantee exactly-once execution at an external provider.
Inspect provider billing before explicitly starting another review.

| Bound | Review contract |
| --- | --- |
| Queue | One active job per scan; two per project; 50 per workspace |
| Deadline | 30 minutes including queue time; no dispatch/publication after expiry |
| Provider calls | At most 20; no automatic provider retry or continuation |
| Findings | 1–1000; at most 50 complete records per batch |
| Context | 180,000 bytes per prompt; 4 MB total prompt budget and encrypted-input plaintext limit |
| Output | Configured per-call ceiling, at most 32,768; total reservation at most 655,360 tokens |
| Graph | At most 100 nodes and 100 edges within 20 KB, with omitted-record counts |
| Retention | Encrypted job inputs cleared seven days after terminal completion; saved review records, receipts and events retained with the scan |

Oversized jobs are rejected without contacting a provider. Per-field context
truncation and omitted graph records are recorded as evidence gaps. Invalid,
refused, incomplete, foreign-ID and duplicate-ID responses cannot publish a batch.
Missing review records remain explicit omissions. These are resource bounds,
not monetary quotas or measured precision/recall guarantees. A worker must be
running to reconcile expired queued jobs; a maintainer can cancel them meanwhile.

The job **Details** view exposes status, cancellation, heartbeat, budget
reservations, provider-native usage counters, digests and an event history.
Missing usage and cost are **unknown**, never zero. Cache and reasoning counters
have provider-specific meanings and must not be summed blindly. No raw provider
body or hidden reasoning is kept in a receipt. A valid provider envelope and
schema remain suggestions requiring human review, not runtime verification.

### Compare saved review results

Choose a run's **Details** button to inspect its own saved results. A later review
can replace the finding's current suggestion; it cannot rewrite the earlier run's
retained narrative. The result panel shows the model verdict, explanation,
remediation, supporting/contrary evidence, missing evidence and the source excerpt
supplied to that run. **Download saved evidence** exports the verified record and
its digest. Long summaries identify shortened metadata; the saved evidence keeps
the bounded input actually supplied to the model.

Current finding status and the current human AI-review decision appear separately
and are labeled as current at load. The panel identifies a replaced suggestion,
changed source evidence or a finding that has since been deleted. Use **Refresh
results** to refresh that comparison. Removing project access prevents subsequent
history reads; a scan transferred to another project does not transfer its prior
project-bound review evidence.

Every valid returned result is retained atomically with its call receipt, job
counters and audit event. Results that would replace an accepted or rejected human
decision are saved as **human decision preserved** without changing the finding.
New jobs count these as completed reviews and distinguish them from published
suggestions. Missing provider results remain omissions. Legacy jobs retain their
earlier publication-count semantics and visibly report unavailable history.
An insertion failure rolls back all suggestions from the batch; the worker keeps
the discarded call receipt and does not automatically repeat the paid request.

Saved records bind the job, call, finding, input/source/prompt/response identities
and model. Narratives and supplied evidence are encrypted under
`ENCRYPTION_SECRET`; listing metadata contains bounded location and verdict fields.
Record digests and authenticated ciphertext are checked before returning details.
Application writes and a database trigger prevent updates to retained records.
This is not external immutable storage or protection against a database
administrator who can change the schema and keys.

History uses project viewer authorization. `GET /api/llm-jobs/{id}/reviews`
returns at most 20 metadata entries with a cursor; each
`GET /api/llm-jobs/{id}/reviews/{reviewId}` returns one verified record, bounded
to 2 MiB of stored plaintext. Both endpoints use `Cache-Control: no-store`.
No raw provider bodies or hidden reasoning are archived. Operator scan deletion
cascades to these records; deleting only a finding retains its historical review.
Backups preserve the records and their update protection. Keep the installation
key for every backup that uses it.

Per-finding evidence survives expiration of the full encrypted job input. Once
that seven-day input expires, the retained digests and per-finding excerpts do
not reconstruct the entire original batch prompt or graph context. Retain a
verified backup before expiry if full-input replay is required. Provider
nondeterminism and uncalibrated model confidence remain separate evaluation work.

## Scan a connected project

1. A project administrator connects the project repository and grants project roles.
2. Each scanning maintainer connects their own GitHub.com or GitLab.com account.
3. Select **Start source scan**. The request immediately returns a saved job and
   opens its scan page.
4. Follow the progress stages and activity log. Maintainers can cancel an active
   job or retry an incomplete scan at the same pinned commit.

The worker reads only the requesting account's repository credential. It rechecks
project permission, account admission, archival and repository identity when claiming,
renewing and publishing a job. Removing project access or account admission stops
further publication. Browser/CI
uploads use the same artifact publication transaction as worker results.

The built-in repository connector currently supports GitHub.com and GitLab.com.
For private forge installations, run the scanner in that forge's CI and upload
SARIF using a project-bound CI credential.

## Recovery and publication

Each worker runs one job at a time; a project has at most one active queued source
scan. A job has a two-minute lease, renewed every ten seconds. A restarted worker
can claim an expired lease. Lease tokens fence progress, source and final result
writes, so an older process cannot publish after recovery or cancellation.

The first resolved commit is saved before its tree is fetched. After fetching,
the exact file bytes are hashed and encrypted in the database. Retries reuse this
snapshot; an interruption before snapshot storage refetches the pinned commit.
There are at most three attempts, each with a fifteen-minute deadline. Failure
and exhausted attempts remain visible; they cannot become an empty successful scan.

Findings, identities, graphs, endpoints, absence updates, final audit and job
completion commit together. A late import error rolls all of them back. A scan
requested before a newer completed scan does not replace that newer baseline.

## Analysis scope and limits

The service runs the trusted Python `ScanEngine` with bundled rules, AI disabled,
an in-memory analysis store, low-severity inclusion, a 50,000-context taint bound,
and finding limits of 500 per rule and 200 per file. Reaching a bound is reported
as partial analysis. Repository configuration, custom rules, builds and application
code are never executed or auto-loaded. Use the CLI and project CI upload workflow
for operator-reviewed custom configurations and larger source scopes.

The fetcher admits source/config extensions and excludes dependencies, build
outputs and lockfiles. It fetches at most 1,000 files, 500 KiB per file and 10 MiB
in total. Provider requests reject redirects and have bounded body sizes and
twenty-second deadlines. Unsupported source languages, failed file fetches,
truncated trees and input limits remain visible as coverage gaps.

This provider-selected snapshot declares `analysisScope: files`. It can update
observed findings, but it cannot prove that unseen historical findings are absent.
Existing CLI/CI reports can declare their broader completed scope separately.
PHP remains unsupported; a DVWA backend scan is not a complete supported scan.

## Evidence and retention

The scan page exposes commit, source snapshot and report digests. Its job API also
records the worker's engine/rule/parser fingerprints and analysis configuration.
These identify the analysis inputs; they do not establish detection accuracy or
runtime impact. Source code and credentials are omitted from activity messages.

Encrypted source snapshots expire seven days after completion, failure or
cancellation. The worker clears expired source payloads during hourly housekeeping.
Source manifests, result manifests, audit records and scan results remain until
the project is explicitly removed. The [backup and recovery procedure](/operations/backup-recovery)
includes access invalidation and an isolated restore drill. Full configurable
retention and deployment-specific recovery objectives remain separate acceptance
work. Protect the original encryption secret separately from archives. Losing it
prevents snapshot recovery and decryption of saved integration settings.

## Local development

Install the locked scanner virtualenv at `scanner/.venv` and the dashboard's locked
Node dependencies. Export the same database and auth environment as the dashboard,
run `npm run db:prepare`, then run `npm run worker` from `dashboard/`.
Run `npm run worker:ai` in a separate process for AI finding reviews.
The worker uses the fixed repository virtualenv path and passes no OAuth or
integration credentials to its Python child. Windows hosts should use the container.

The worker's native TypeScript entry uses explicit relative `.ts` imports, following
[Node's type-stripping contract](https://nodejs.org/api/typescript.html).
Docker-specific context exclusion follows the
[Docker build-context contract](https://docs.docker.com/build/concepts/context/).
