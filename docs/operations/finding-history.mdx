## What remains stable

A scan stores observations. On a project's default branch, observations also
refer to a persistent finding identity, which holds triage status, reason,
expiry, decision history, owner/team, due date, priority, tags and ticket metadata.
A new CI runner or worker directory should not
create a new decision for unchanged source evidence.

The scanner emits `aegifyFingerprint/v2` alongside the historical
`aegifyFingerprint/v1` SARIF key. The dashboard recomputes the v2 identity from
retained evidence. Its inputs are:

| Input | Identity behavior |
|---|---|
| Project | Database identities never cross project boundaries. |
| Exact rule ID | Different rules remain separate, including case differences. |
| Repository ID | Use stable workspace manifest IDs for multiple repositories. |
| Repository-relative module path | Moving the checkout root preserves identity. Renaming the module creates a new identity. |
| Full retained source snippet, or message when no snippet exists | Content changes can create a new identity. Line numbers are not inputs. |

Evidence normalization preserves case, numbers and internal whitespace, including
string literal contents. Only line endings and outer ASCII whitespace normalize.
This is a content identity, not a semantic equivalence proof: formatting changes
can produce new identities, while repeated identical snippets in the same module
and rule can share one identity. Their individual observations and locations
remain available in the scan.

For an ordinary single-repository project, the repository ID can be empty.
For multiple repositories within one project, assign distinct stable IDs in the
[workspace manifest](/concepts/multi-repository). An importer cannot infer two
different repositories from identical unqualified relative paths.

If a report has no usable logical path, its physical path remains part of the
identity. Unknown absolute paths are not shortened to a guessed basename. Other
supported SARIF producer hints are hashed together with rule, repository and
path, so one shared line hash cannot silently join those namespaces.

## Upgrading existing installations

Run the normal database migration process before starting the updated dashboard
and workers. Back up the existing database first using the
[backup and recovery procedure](/operations/backup-recovery).

The scope migration keeps identity IDs, fingerprints and all triage history. It
backfills a repository/module scope only where every retained historical
observation agrees on the same rule and valid logical scope.

On a subsequent default-branch import, a legacy identity upgrades when retained
source evidence and scope establish a one-to-one match. The identity ID, triage
reason, actor, expiry and event history remain attached. The audit event
`finding.identity.migrated` records the old and new fingerprints. Findings,
identity upgrades, graphs, scan completion and audit events publish in the same
transaction; a late failure rolls them all back.

If more than one old identity could match, historical namespaces conflict, or
required retained evidence is unavailable, the importer preserves historical
decisions and leaves the new identity open. The scan becomes `partial`, with
`finding_identity_review_required`, and writes
`scan.identity_migration.review_required` to the audit log. Review the old and
new evidence before assigning a new triage decision. No conflicting decisions
are automatically merged.

Automatic legacy matching is bounded to 5,000 candidate identities and 5,000
retained observations per import, with 16 KiB per retained snippet/message.
Exceeding the candidate/observation budget preserves all old decisions and marks
the incoming missing identities for review. These are migration limits, not
detection limits. A missing source namespace cannot always be recovered when
both the old checkout path and producer fingerprint have changed.

## Absence and incomplete analysis

New scanner reports include a versioned `analyzedSources` inventory pairing
physical paths with repository IDs and relative modules. The importer checks
that each analyzed file has exactly one logical identity. Contradictory finding
provenance is rejected; malformed inventories make coverage partial.

An observed identity supersedes its previous occurrence even when the new scan
is partial. Marking an unobserved identity absent requires a complete analysis
on the project's default branch, with no coverage gaps and an explicit list of
evaluated rules. Only the analyzed repository/module/rule scope is reconciled.
An unchanged relative module in another repository, an excluded file, a disabled
rule or a feature branch does not establish absence.

Legacy reports without the logical inventory retain physical-path reconciliation
only for observations and identities without a repository ID. They cannot mark
repository-qualified evidence absent or establish that an unknown new checkout
is the same old scope.

## Team assignment and triage

The identity holds the current workflow. A successful default-branch scan copies
that workflow into its new observations. Saving a decision or assignment updates
the identity and all its current observations together, with an audit event in
the same transaction. Assignment audit details retain the before/after values.
Older observations retain their saved fields and source
evidence. Opening an older observation displays the current issue's controls and
labels the historical status and owner separately.

Project triagers and higher roles can edit active projects. Viewers and archived
projects are read only. Membership and account admission are checked again inside
the write transaction. An unchanged rescan keeps the workflow version. Human
changes, ticket linkage, an established absence or automatic reopening invalidate
stale drafts; an outdated save returns `409` without changing stored data.

False-positive and accepted-risk decisions require a rationale. Expired decisions
reopen on the next observation and clear their active expiry, so later scans do
not repeatedly expire the same decision. The prior decision remains in the event
history. The importer does not run a wall-clock scheduler that expires decisions
between scans.

Findings without an identity, including feature-branch observations, have a local
workflow only. Assignment and status updates affect that observation; they do not
carry into another scan. Their decision rationale is retained in the audit event,
and time-bounded triage is unavailable until there is a persistent identity.

### API compatibility

`GET /api/findings/:id` returns `workflow` and `permissions.canTriage` in addition
to the saved observation. Use the workflow fields for current controls; the
top-level fields may describe a historical observation.

`PATCH /api/findings/:id` now requires the exact `workflow.version` returned by
GET as `expectedVersion`. Existing API clients must fetch it before editing. For
example, send an assignment update with this JSON body after replacing the version:

```json
{
  "expectedVersion": "identity:YOUR_ID:CURRENT_REVISION",
  "owner": "Payments team",
  "priority": "p1",
  "dueAt": "2026-12-01",
  "tags": ["auth", "release-review"]
}
```

Requests are bounded to 32 KiB. Owner/team names allow 200 characters; tags allow
20 values of 50 characters each; rationales allow 4,000 characters. Dates accept
`YYYY-MM-DD` or UTC ISO strings with milliseconds. Invalid fields, dates and
missing versions return `400`. On `409`, review a fresh GET before resubmitting.
The dashboard preserves the rejected draft; **Reload latest** explicitly replaces
unsaved triage and assignment drafts.

### Existing assignment data

The additive workflow migration copies a unique, bounded nonempty assignment
tuple from the identity's latest scan only when its logical source scope is
known. Empty duplicate observations do not override a recorded assignment.
Conflicting, malformed or unbound metadata stays in its original observations
and sets `workflowNeedsReview`; it is not chosen automatically.

The finding page shows the review notice. Review the historical records, choose
the current assignment, and use **Save reviewed assignment**. The API equivalent
is an assignment patch with `resolveWorkflowReview: true`. A routine assignment
patch does not clear the notice. This review flag concerns assignment continuity;
identity-attribution uncertainty still appears separately in scan health.

### Ticket continuity and delivery limits

A recorded Jira key and URL follow the identity across scans. A later ticket
request returns the existing linkage. Successfully received ticket details are
audited even when a concurrent linkage prevents attaching that receipt; the
existing ticket is kept and `finding.ticket.link_review_required` records the
other completed action.

Remote issue creation and the local database transaction are separate. Concurrent
requests that both start without a ticket can still create separate issues, and
a timeout or database outage can leave a remote issue without a local receipt.
There is no durable outbox or exactly-once delivery guarantee. Review Jira before
retrying an uncertain result. Migrated ticket conflicts require operator review
of the retained observations/audit data; choosing an assignment does not select
or reconcile an ambiguous remote ticket. These remain follow-up integration work.

## Current scope

Migration diagnostics appear in scan health and audit events. A dedicated source
identity conflict-resolution interface, driver-qualified multi-tool identities,
and semantic invalidation when rule/model behavior changes remain follow-up work.

These checks establish data continuity and isolation. Detection precision,
recall and AI review quality require the separate
[evaluation contract](/analysis/benchmark-evaluation).
