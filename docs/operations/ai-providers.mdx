## Protocols and services

Settings → AI review supports four implemented wire protocols. Service presets set
an endpoint and protocol; they do not claim a separate native adapter for every vendor.

| Protocol | Operation | Authentication on the default host |
| --- | --- | --- |
| Anthropic Messages | `/v1/messages` | Stored Anthropic key |
| OpenAI Chat Completions | `/v1/chat/completions` | Stored OpenAI key |
| OpenAI Responses | `/v1/responses` | Stored OpenAI key |
| Google Gemini | `/v1beta/models/MODEL:generateContent` | Stored Google key |

Presets cover Anthropic, OpenAI Responses/Chat, Google Gemini, Azure OpenAI v1,
OpenRouter, Groq, and a custom HTTPS gateway. Azure uses the deployment name as
the model ID and an explicit `api-key` custom header. OpenRouter and Groq use a
dedicated `Authorization: Bearer ...` custom header. Do not paste an API key into
the endpoint field. Legacy Azure endpoints that require a dated `api-version`
query are not part of the Azure v1 preset.

Choose an exact model identifier available to your account. The UI does not guess
a "latest" model, silently replace a model on provider change, or assert that a
particular model is enabled for your account. Set the request timeout, output token
budget, and—when using Chat Completions—the token parameter accepted by the model:
`max_tokens` or `max_completion_tokens`.

API origins, versioned base paths, and complete operation URLs are supported without
duplicating `/v1`. The request URL preview shows the resulting URL before saving.
OpenAI Responses requests use `store: false`. This is not a guarantee about all
provider retention policies. Tool calls and thought parts are not executed or
treated as answer text. No new autonomous tool-execution workflow is enabled.

## Credentials and egress

Direct-provider keys are only attached to the built-in default endpoints. Any custom
endpoint—including a preset vendor endpoint—uses only explicitly entered custom
headers. Those headers are encrypted and are never returned to the browser, even
for legacy plaintext records. Changing endpoint/protocol requires explicitly
replacing or removing existing custom headers to avoid forwarding a credential to
another service. Blank untouched secret fields preserve their stored values.

Requests require HTTPS, public DNS addresses, certificate verification, and a
connection pinned to the validated DNS result. Redirects, private/loopback endpoints,
credential-bearing URLs, and unbounded responses are rejected. The transport caps
responses at 2 MiB and does not retry automatically. Use an approved public HTTPS
gateway for a private model deployment; direct local Ollama access is not enabled.
Bedrock SigV4, Vertex service-account authentication, and native local-model
protocols are not advertised as implemented adapters.

Saving validates configuration; it does not contact an external service. "Test
saved connection" asks for confirmation and sends a small structured-response
probe using saved settings. This can incur usage. Unit tests use mocked provider
responses, and do not establish real credentials, quota, or model availability.

## Scanner agent adapters

`aegify agent-run` has its own scanner-side OpenAI, Anthropic and CLI adapters.
These are separate from the dashboard's provider settings and transport above.

The OpenAI Responses adapter requests strict structured output with all four
narrative fields required: `summary`, `claims`, `evidence_gaps`, and
`recommendations`. Empty lists must be present. The Codex output schema uses the
same contract. Local artifact models retain defaults so older saved narratives
can still be read. New OpenAI, Codex and Claude Code responses must contain all
four fields, without extra keys, duplicate keys, non-JSON numbers or Markdown
wrappers. Pydantic's text/list limits remain enforced locally.

OpenAI results need a completed response and one completed assistant message.
Refusals, provider errors, incomplete output, unexpected tool calls, multiple
messages and inconsistent status fields do not produce a narrative. Reasoning
items are ignored, not used as answer text. Requests retain `store: false`, a
4,096-token output limit and a 2,000,000-byte response cap. Redirects are rejected.
HTTP/provider errors retain a bounded diagnostic without copying remote bodies.
The socket timeout is not a durable job deadline or a provider-wide spend budget.

Claude Code requires a successful result envelope, `is_error: false`, no API error,
and an absent or completed stop reason. A refused or unfinished result is rejected
even if its text happens to contain a complete JSON object. Codex must exit
successfully and supply the complete message file; it does not yet provide a
separate provider-status/usage receipt to Aegify.

| `backend_error_code` | Meaning |
| --- | --- |
| `refused` | The provider declined the review |
| `incomplete` | The provider did not finish its response |
| `invalid_response` | The response shape, encoding or message file was invalid |
| `response_limit` | Output exceeded the configured byte bound |
| `provider_error` | The provider failed or returned an unsuccessful envelope |
| `timeout` | API socket or CLI invocation timeout |
| `process_error` | CLI launch, I/O or exit failure |
| `unsupported_platform` | CLI process controls are unavailable on this platform |

The new field defaults to an empty string for historical artifacts and failures
outside these adapters. Failed model enrichment leaves static evidence intact.
Empty failure codes are omitted from the artifact digest to preserve historical
v1 digests; a nonempty failure code is included.
`agent-run` writes the retained artifact before exiting: `0` means completed,
`3` means partial or awaiting approval/evidence, and `2` means failed input,
configuration or execution. Previously a partial review could exit `0`; CI
consumers must handle `3` explicitly and must not equate it with a completed review.
Offline tests cover strict schemas, refusal/incomplete/error envelopes, malformed
JSON, output flooding, a blocked input pipe, deadlines, owned child cleanup and
message-file limits. They invoke no provider and execute no analyzed source.
POSIX process groups cannot contain a program that deliberately detaches; dedicated
worker/container isolation, provider usage accounting, cancellation and durable
job recovery remain required for a multi-tenant installation.
