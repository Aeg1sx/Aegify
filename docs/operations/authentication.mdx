## Access boundary

A self-hosted installation contains one workspace with explicit project membership.
The sign-in allowlist admits an account; project roles determine which scans,
findings, graphs, endpoints and AI jobs it can access. Set `AUTH_ADMIN_EMAILS` to
exact administrator email addresses that also satisfy `AUTH_ALLOWED_EMAILS` or
`AUTH_ALLOWED_DOMAINS`. Workspace administrators manage integrations, shared rules,
project creation and recovery. Every API checks authorization at the data boundary.

| Project role | Permissions |
| --- | --- |
| Viewer | Read the project's results, evidence, endpoints, graphs and job history |
| Triager | Viewer access plus finding status, assignment and ticket actions |
| Maintainer | Triager access plus SARIF uploads, API contract imports and AI reviews |
| Admin | Maintainer access plus project settings, membership and CI credentials |

In a project, use **Project access** to add an existing admitted account by email.
Access changes take effect on the next request. Assign another administrator before
removing the last project administrator. `AUTH_ADMIN_EMAILS` remains the operator's
recovery path. Service credentials belong to the project and must be revoked
separately when a CI integration is retired.

On upgrade, recorded project owners become project administrators. Unowned legacy
projects and unlinked scans are visible only to workspace administrators. An admin
must explicitly delegate those projects; existing users do not acquire access to
other teams' data. Back up the database and encryption secret before migration.

There is no default username or password and no unrestricted public registration.
Development without `AUTH_SECRET` retains the existing unauthenticated preview mode;
bind that mode to loopback only. Production refuses to start without authentication,
encryption, a valid origin, and an explicit access policy.

## Required configuration

Generate independent `AUTH_SECRET` and `ENCRYPTION_SECRET` values with
`openssl rand -hex 32`; keep them in an ignored environment file or a secret manager.
`AUTH_URL` must be the exact external HTTPS origin. HTTP is accepted only for a
loopback origin. A proxy must preserve that origin and must not expose a second
unprotected path to the application.

Run `npx --no-install prisma migrate deploy` against a backed-up database before
deploying this release. Migrations add project membership, hashed service credentials and access audit
events alongside the account and rate-limit tables without deleting existing accounts.
The switch to bounded JWT sessions signs existing database-session users out once.

## Username and password

Set `AUTH_LOCAL_ENABLED=true`, `RESEND_API_KEY`, and `AUTH_EMAIL_FROM` (a bare email
address on a verified Resend sending domain). Add the owner's email to
`AUTH_ALLOWED_EMAILS`. Visit `/auth/request-access` to request an activation link.

The email link opens `/auth/activate`. Only after proving email ownership does the
user choose a username and password. Passwords use a unique salt and Node's scrypt
KDF (`N=32768, r=8, p=3`, 32 MiB profile). Passphrases must be 15–128 characters.
No password or raw verification token is returned through the settings API.

Activation and reset links expire after 30 minutes, are purpose-bound, and are
consumed atomically once. Only token hashes are stored. Tokens travel in the URL
fragment and are removed from browser history after the form loads. Merely opening
a link does not consume it, which avoids accidental consumption by email scanners.

`/auth/forgot-password` sends a reset link only for an eligible verified password
account. Resetting a password increments the account's session version and
invalidates every existing session. An SSO-only account cannot acquire a password
through this recovery route. Email requests return a generic eligibility message;
check the mail provider dashboard for delivery failures.

## Google OAuth and Okta SSO

| Provider | Environment | Registered callback |
| --- | --- | --- |
| Google | `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` | `AUTH_URL/api/auth/callback/google` |
| Okta OIDC | `AUTH_OKTA_ID`, `AUTH_OKTA_SECRET`, `AUTH_OKTA_ISSUER` | `AUTH_URL/api/auth/callback/okta` |

Create an OIDC web application in Okta and use its exact issuer, including the
authorization-server path when applicable. Both providers request `openid email
profile`, use PKCE/state/nonce checks, and require a verified email claim plus the
workspace allowlist. Configure the Okta application to emit `email_verified=true`
only for verified identities. Enforce MFA and device policies in the identity
provider; this release does not claim to implement local MFA or SAML.

GitHub and GitLab sign-in remain available with their existing environment variables.
All providers are subject to the workspace allowlist. Existing GitHub/GitLab
repository scopes are retained for repository integration. Google and Okta request
identity scopes only. Accounts with matching email addresses are not merged
automatically: use the existing sign-in method. Provider registration and real
callback validation require operator-supplied credentials; fixture tests are not
evidence of a working production SSO configuration.

## Session and request controls

Sessions have an eight-hour absolute maximum, encrypted Auth.js cookies, and a
durable per-user revocation version checked on every session read. Cookies use the
Auth.js HTTP-only, SameSite, and HTTPS-aware Secure defaults. Settings → Security
provides a "Sign out all sessions" action for the current account.

Local account actions require same-origin JSON requests with an 8 KiB body limit.
Auth.js supplies CSRF protection for sign-in/sign-out. Authentication failures do
not disclose whether a password account exists. Rate limits are persisted in the
database: 10 attempts per identifier per 15 minutes, 100 per client per 15 minutes,
three email requests per address per hour, and a shared global cap. Counter keys
use an HMAC and expired windows are cleaned up. Untrusted forwarded IPs are ignored.

Enable `AUTH_TRUST_PROXY=true` only when a trusted ingress overwrites
`X-Forwarded-For` and direct access is blocked. Otherwise clients share a conservative
bucket. Add ingress body limits and global request throttling for production; these
application controls do not replace network-layer availability protection. Keep
OAuth account tokens and database backups protected by encrypted storage and narrow
filesystem access. No real email or identity-provider request is made by unit tests.

Implementation references: [Auth.js Credentials](https://authjs.dev/getting-started/authentication/credentials),
[Google](https://authjs.dev/getting-started/providers/google),
[Okta](https://authjs.dev/getting-started/providers/okta), and
[OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).


## CI service credentials

Open a project as its administrator and create a named **CI upload token** with
an expiry of 7, 30 or 90 days. Copy the credential once into the CI secret manager.
A token has only `scan:upload` permission for that project. Token listings and audit
events contain metadata, never the raw credential or its stored hash. Each project
can have up to 50 active credentials. Revocation, expiry and project archival reject
future uploads. Restore does not revive an explicitly revoked token.

Use the installed scanner CLI to send a previously generated report:

```bash
# AEGIFY_UPLOAD_TOKEN is injected by the CI secret manager.
aegify upload results.sarif \
  --dashboard-url https://aegify.company.example \
  --project-id PROJECT_ID \
  --branch "$CI_COMMIT_REF_NAME" \
  --commit "$CI_COMMIT_SHA"
```

The token already binds its project; a conflicting `--project-id` is rejected.
`aegify scan --upload-dashboard` also reads `AEGIFY_UPLOAD_TOKEN`,
`AEGIFY_DASHBOARD_URL`, and optional `AEGIFY_PROJECT_ID`. Credentials are sent only
to the exact HTTPS origin (loopback HTTP is allowed for local checks); redirects
are rejected. Install the organization's CA in the runner trust store when needed.
Do not disable TLS verification. Upload failure exits with code 4; a successful
upload is a delivery receipt and does not mean the scan passed its security gate.
Preserve the original scan exit code in CI: 1 blocks on findings, 2 fails analysis,
and 3 means incomplete coverage.

The old environment credential works only when both `AEGIFY_UPLOAD_TOKEN` and
`AEGIFY_UPLOAD_PROJECT_ID` are configured on the dashboard. This is a migration
bridge with operator-managed rotation. Prefer expiring credentials created in the
project. Bearer credentials cannot read dashboard APIs, create projects, change
shared rules, or modify integration settings. Member/service uploads never replace
the workspace rule definitions from untrusted report metadata.

Project administrators can inspect recent membership, token and import events in
the project screen. Events contain stable actor and resource IDs and survive project
deletion in the database. These application records require the same protected
backups as the database; they are not an external immutable audit sink.
